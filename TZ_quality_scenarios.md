> (ВКР). Перед началом обязательно прочитай разделы 0–2, затем реализуй по

## 0. Контекст дипломной работы (зачем это всё)

Тема ВКР — **анализ логов и предиктивный анализ (predictive maintenance) на
структурированных JSON-логах симулированного завода**. Стек ML (отдельный этап,
сейчас НЕ реализуем): Loki API → pandas → PyOD (ECOD + Isolation Forest) +
Prophet. Логи уже structured JSON, парсер Drain не используется.

Симулятор — это **генератор размеченного датасета**. Он имитирует завод
по производству автомобильных шестерён (spur + helical) и льёт события в логи.
ML-модель учится на **логах**, находя связь «аномалия в сенсорах → брак детали».

Ключевая идея этой задачи: добавить **управляемые сценарии поломок** на станках.
Когда сценарий активен, у станка согласованно искажаются (а) сенсорные данные и
(б) результаты измерений деталей — так, чтобы между ними была причинно-следственная
связь, которую ML-модель сможет выучить. Плюс есть редкий **фоновый брак** без
причины — это шум, который модель должна научиться игнорировать.

**Что важно для оценки:** не точность имитации реального завода, а наличие в
логах выучиваемой связи «сенсор → дефект» + чистая, понятная архитектура.

## 1. Текущая архитектура (как есть сейчас)

Монорепо `log-monitoring`. Запуск — `docker compose up`.

- **`simulator/`** — in-memory модель завода в фоновом потоке (`loop.py`).
  Подсистемы тикают по очереди каждые `TICK_REAL_SEC` (0.1 c):
  `orders → production → equipment → furnace → maintenance → quality → scenarios`
  (точный список и порядок — в `simulator/main.py`).
  - `state.py` — общее состояние (под `state.lock`): `machines`, `batches`,
    `queues` (deque на каждую очередь), `pending_spot_checks`,
    `pending_inspection_measurements`, `pending_tool_change_requests`, `counters`.
  - `config.py` — все константы (маршрут, тайминги, профили сенсоров, спеки измерений).
  - `domain/` — dataclass'ы `Batch`, `Machine`, `WorkOrder`, `Order`, `FurnaceLoad`.
  - `subsystems/` — `orders`, `production`, `equipment`, `furnace`, `maintenance`,
    `quality`, `scenarios`.
  - `client.py` — `FactoryClient`, шлёт события в 4 FastAPI-сервиса (буферизует
    measurement, остальное POST'ит сразу).
  - `webui/` — `index.html`, `app.js`, `style.css` (пульт управления).
- **`services/`** — 4 FastAPI-сервиса (`equipment`, `production`, `quality`,
  `maintenance`). Принимают события, пишут в Postgres и/или в логи.
- **`postgres/init/init.sql`** — схема БД (machines, machine_status,
  active_batches, open_work_orders).
- **`loki/`, `promtail/`, `grafana/`** — стек логов (НЕ трогаем в этой задаче).

### Маршрут производства (config.ROUTE)
`turning → hobbing → shaving → heat_treatment → grinding → inspection`
Единый для всех типоразмеров (SPUR-S, SPUR-M, HEL-M, HEL-L). Печь
(`heat_treatment`) обслуживается отдельной `FurnaceSubsystem`, остальное — общей
`EquipmentSubsystem`. `production` назначает партии из очереди ПЕРЕД станком
(словарь `QUEUE_BEFORE` / `QUEUE_TO_MACHINE_TYPE`) на свободный станок этого типа,
сортируя очередь по приоритету (rush → urgent → normal).

### Как качество работает СЕЙЧАС (это переделываем)
- `equipment._transition_to_cooldown` ставит spot-check в `pending_spot_checks`
  после стадий из `SPOT_CHECK_STAGES = ["hobbing", "heat_treatment"]`.
- финальная inspection: `production._start_batch_on_machine` генерит 10%-выборку
  (`inspection_sample_indices`), equipment кладёт детали выборки в
  `pending_inspection_measurements`.
- `quality._measure_part` берёт СЛУЧАЙНЫЕ параметры из общего списка
  `ALL_MEASUREMENT_PARAMS`, генерит значения почти всегда в допуске; fail —
  только фоновый (`BACKGROUND_FAIL_RATE`).
- measurement пишется **только в логи** (см. `services/quality/main.py` —
  «БД не трогает»).
- `scenarios.py` — каркас с `anomaly_modifier`, НЕ подключён к генерации.

- ML-сервис — следующий этап. Сейчас только готовим логи и данные.
- Базовую логику `production` (очереди/приоритеты) — оставляем.

Сейчас в `MEASUREMENT_SPECS_BY_PRODUCT` только 5 геометрических параметров.

| Параметр | Где появляется | Диапазон/допуск | Направление при fail |
|---|---|---|---|
| `blank_runout` | turning (биение заготовки) | задать допуск (мкм), напр. ~20 мкм | только ↑ |
| `profile_deviation` | hobbing | как есть в конфиге | только ↑ |

> ВАЖНО про семантику спеки. Сейчас геометрия задана как `(nominal=0, tolerance, unit)`:

> Предлагаемый формат: для диапазонных параметров хранить `(min, max, unit)` и
> отдельный флаг типа параметра (`range` vs `deviation`). Решение по структуре
> оставляю на исполнителя, но геометрия и диапазонные должны различаться при
> генерации значения и при проверке pass/fail.

Добавить новые параметры в `MEASUREMENT_SPECS_BY_PRODUCT` для всех 4 product_code
(твёрдость/слой можно сделать одинаковыми для всех типоразмеров; геометрию —
как уже масштабировано).

## 4. Новая модель контроля качества

### 4.1. Базовый режим (БЕЗ активного сценария)

После **каждого** этапа (turning, hobbing, shaving, heat_treatment, grinding)
партия отправляется на измерительный станок (M-GMM) и встаёт в очередь перед ним
(как любой другой этап — через механизм очередей `production`). Измерение —
полноценная операция, занимающая M-GMM (время = число измеряемых деталей ×
время-на-деталь; см. раздел 7).

- Промежуточные этапы: проверяется **1 случайная деталь** по параметрам этого
  этапа (Таблица A). Если она фантомно (фоново) забраковалась — проверяются
  **2 соседние**, и они **всегда pass** (force_pass). Это сохраняет текущую
  логику `_do_spot_check`, но параметры теперь определяются этапом, а не случайно.
- **Финальная inspection** (после grinding): **10%-выборка** всей партии, по
  всем 8 параметрам. Всегда.

### 4.2. Фоновый брак

Очень редкий, без причины, **сенсоры НЕ искажаются** (станок в норме). Но в
измерениях ОДИН случайный параметр (из доступных на этапе) выходит за допуск —
иначе деталь формально годная. Отклонение **лёгкое** (`uniform(0.05, 0.25)` за
границу) и в физически верную сторону (см. таблицу направлений в разделе 3).
`reason="background_random"`, `source_machine_id=NULL`, `scenario_id=NULL`.

**Ставка фона делится на этапы:** общий целевой фон ~1.5% за маршрут, этапов 5 →
`BACKGROUND_FAIL_RATE = 0.003` (0.3%) на каждый этап. Разыгрывается на каждой
проверке для проверяемой детали.

### 4.3. Режим со сценарием (партийный брак)

Когда на станке активен сценарий, обычная проверка «1 случайная деталь»
на этом этапе **ОТМЕНЯЕТСЯ** и заменяется специальной логикой.

Каждая деталь, обработанная станком **в момент активного сценария**, помечается
как бракованная (метка ставится В МОМЕНТ ОБРАБОТКИ, не измерения; деталь,
попавшая под старт сценария в середине цикла, тоже считается бракованной).

Когда партия дошла до измерения после этого этапа:
- **Все помеченные (отбракованные) детали меряются ПОГОЛОВНО** → каждая fail с
  причиной сценария. Это основные данные для ML (по ним строятся логи).
- **Остальные (годные) детали** → 10%-выборка → все pass.

Два случая по охвату:

- **Случай A — сценарий захватил ЧАСТЬ партии** (например 30 из 80). Партия
  дорабатывается (остаток после ремонта — годный, см. раздел 6). На измерении:
  поголовно отбракованные (30) + 10% от годных (50).
- **Случай B — сценарий захватил ВСЮ партию** (крайний: запущен на свободном
  станке в начале партии). Вся партия = fail (поголовно). Выборки по ней НЕТ.
  И на **СЛЕДУЮЩУЮ** партию, что придёт на этот станок, обычная «1 деталь»
  заменяется на **10%-выборку единоразово** (подтвердить, что станок после
  ремонта в норме; там всё pass + возможный фон). После — обычный режим.
  → Нужен флаг на станке, напр. `verify_next_batch_with_sample: bool`.

### 4.4. Согласованность сенсоров и измерений

Это **ядро ценности для ML**. При активном сценарии:
- сенсоры станка искажаются по словарю сценария (через существующий
  `machine.anomaly_modifier`, умножается в `equipment._generate_sensor_readings`);
- измерения отбракованных деталей искажаются по словарю того же сценария
  (только параметры из набора причины, в указанную сторону).

Параметры/сенсоры, НЕ перечисленные в сценарии, остаются в норме. Не «всё
разъехалось» — только подпись конкретной причины.

## 5. Система сценариев (scenarios.py + config.py)

### 5.1. Словарь сценариев (config.py)

Завести реестр сценариев, организованный **по типам станков**. Каждый сценарий
несёт: имя причины, набор искажаемых сенсоров (множители), набор искажаемых
измерений (параметр → направление), время наладки (для maintenance WO).

**Таблица B — 11 сценариев.** «↑↑» = сильнее обычного.

**TURNING (1):**
| Сценарий | Сенсоры (множители к норме) | Измерения |
|---|---|---|
| `tool_wear` | vibration_rms ↑, spindle_load ↑, spindle_bearing_temp ↑ | blank_runout ↑ |

**HOBBING (3):**
| Сценарий | Сенсоры | Измерения |
|---|---|---|
| `hob_wear` | vibration_rms ↑, spindle_load ↑, hob_bearing_temp ↑ | profile ↑, pitch ↑ |
| `chatter` | vibration_rms ↑↑, spindle_load ↑ | profile ↑ |
| `workpiece_loose` | vibration_rms ↑, work_spindle_rpm нестаб. | runout ↑, lead ↑ |

**SHAVING (1):**
| Сценарий | Сенсоры | Измерения |
|---|---|---|
| `shaver_wear` | vibration_rms ↑, spindle_load ↑ | profile ↑, lead ↑ |

**FURNACE (3):**
| Сценарий | Сенсоры | Измерения |
|---|---|---|
| `under_carburizing` | carbon_potential ↓, furnace_temp ↓ | surface_hardness ↓, case_depth ↓ |
| `over_carburizing` | carbon_potential ↑, furnace_temp ↑ | surface_hardness ↑, case_depth ↑, core_hardness ↑ |
| `quench_distortion` | quench_oil_flow ↓↓, quench_oil_temp ↑ | runout ↑, lead ↑ |

**GRINDING (3):**
| Сценарий | Сенсоры | Измерения |
|---|---|---|
| `grinding_chatter` | vibration_rms ↑↑, wheel_bearing_temp ↑ | surface_roughness ↑, profile ↑ |
| `coolant_loss` | coolant_flow ↓↓, coolant_temp_c ↑ | surface_roughness ↑, runout ↑ |
| `grinding_burn` | coolant_flow ↓, spindle_power_kw ↑↑ | surface_hardness ↓, surface_roughness ↑ |

> `grinding_burn` специально роняет `surface_hardness`, которую печь подняла —
> перемер твёрдости на grinding (Таблица A) это ловит. Это ценный для ML случай.

Конкретные множители сенсоров и величины отклонений подбери разумными;
ориентир по сенсорам — текущие заглушки в `scenarios.py` (1.4–1.6).

### 5.2. Степень тяжести (severity)

Три уровня: `light` / `clear` / `gross`. Тяжесть масштабирует И множители
сенсоров, И величину выхода измерений за допуск:
- light → `uniform(0.05, 0.25)` за границу допуска;
- clear → `uniform(0.25, 0.6)`;
- gross → `uniform(0.6, 1.2)`.
Тяжесть НЕ влияет на долю брака — доля всегда 100% (если параметр вышел за
допуск, деталь бракуется по определению). Одна тяжесть на запуск.

### 5.3. Лимит и самозавершение

- Лимит сценария задаётся в **количестве деталей** (parts_limit).
- Если `parts_limit > остатка деталей в текущей партии` → **обрезается до
  остатка** (сценарий не может «дожить» до следующей партии).
- Когда через станок прошло `parts_limit` деталей (или партия закончилась
  раньше) → сценарий **сам создаёт maintenance WO** (`reason` = имя сценария) и
  переводит станок в `maintenance`. Время наладки берётся из словаря сценария
  (придумать реалистичное: замена резца/фрезы ~20–40 мин; перекалибровка/печь —
  дольше, до нескольких часов).
- WO от сценария идёт через те же 3 бригады (B-MECH-01..03), единая логика
  `maintenance`. Если бригады заняты — WO ждёт, станок стоит в maintenance дольше.
- После ремонта станок → норма, сценарий снят, партия размораживается (раздел 6).

### 5.4. Авто-режим (опционально, можно вторым шагом)

Авто-генератор сам выбирает: случайный момент, случайный станок, случайный
сценарий из доступных этому типу, одну фиксированную тяжесть, лимит в деталях.
Та же механика самозавершения. Если реализуешь — сделай выключаемым флагом.

## 6. Заморозка партии и выбытие деталей (equipment.py, domain/batch.py)

### 6.1. Новые поля Batch (domain/batch.py)

- `failed_indices: set[int]` — индексы выбывших/бракованных деталей.
- `scenario_marked_indices: set[int]` — индексы деталей, обработанных под
  активным сценарием (с привязкой к scenario_id; можно `dict[int, str]`).
- `is_frozen: bool = False` — партия заморожена (станок в maintenance).
- поля для накопления брака по причинам, если нужно для UI-счётчика
  (например `defects_by_reason: dict[str, int]`).
- убрать привязку к старой выборке, если она больше не нужна
  (`inspection_sample_indices` остаётся только для финала — см. ниже).

### 6.2. Заморозка при tool_wear (ИЗМЕНЕНИЕ текущей логики)

Сейчас: при `tool_wear >= TOOL_WEAR_TRIGGER` ставится alarm + запрос ТО, но
станок **дорабатывает партию до конца** и только потом уходит в maintenance.
Это НЕПРАВИЛЬНО — детали после достижения порога шли бы в брак.

Надо: как только `tool_wear` достигает порога ПОСЕРЕДИНЕ партии →
**немедленно**: создать WO, заморозить партию (`is_frozen=True`), станок →
maintenance. Ни одна деталь в «красной зоне» не обрабатывается (стоп ровно на
пороге). После ремонта (tool_wear сброшен в 0) → разморозка, доработка остатка
с нормальным инструментом (эти детали годные).

### 6.3. Заморозка при сценарии

Когда сценарий исчерпал лимит и создал WO → станок в maintenance → если на
станке ещё остались необработанные детали партии (случай A) → партия
замораживается (`is_frozen=True`). После ремонта → разморозка, остаток
дорабатывается **годным** (станок вылечен, сценарий снят). В партии получается
смесь: «грязное окно» (брак с причиной) + «чистый» остаток (норма).

### 6.4. Механизм pause/resume

Единый для обоих триггеров (tool_wear и сценарий): станок уходит в maintenance →
партия `is_frozen=True`, equipment не продолжает её обработку, пока станок в
maintenance. Когда maintenance завершён (бригада освободила станок) → станок
возвращается в `running` на ту же партию с текущего `parts_done_in_batch`,
`is_frozen=False`. Соседние партии в очереди разбираются другими станками того же
типа по обычной логике production — спец-обработка не нужна.

### 6.5. Выбытие деталей

При fail деталь физически выбывает: `failed_indices.add(idx)`. «Годное
количество» = `quantity - len(failed_indices)`. **НЕ менять сам `quantity`**
напрямую при обработке (на нём держатся счётчики циклов equipment). Передавать
«годное количество» в `batch_completion` (`actual_quantity`) и учитывать при
10%-выборке годных (брать индексы не из `failed_indices`).

## 7. Измерение как операция на M-GMM (equipment.py / production.py / config.py)

Сейчас inspection — отдельный этап только в конце. Теперь измерение происходит
после КАЖДОГО этапа и физически выполняется измерительными станками M-GMM
(`machine_type="inspection"`), вставая в очередь перед ними.

- Время измерения = (число измеряемых деталей) × (время-на-деталь). Время-на-деталь
  — своё для каждой точки контроля (сейчас единое `CYCLE_TIME_SEC["inspection"]=60`).
  Завести в config тайминги по этапам, например
  `INSPECTION_TIME_PER_PART_SEC: dict[stage, sec]` (значения подобрать; владелец
  приводил черновой ориентир 4/6/8 мин для разных точек — это время-на-деталь).
- Число измеряемых деталей:
  - базовый режим промежуточного этапа: 1 (или 3 при фантомном fail);
  - финал: 10% от партии;
  - при сценарии: (все отбракованные) + 10% годных.
- Если M-GMM станет узким горлышком — владелец добавит станок через config.MACHINES
  + кнопку «Sync Fleet» (парк динамический, `POST /register-machines`). Менять
  логику под это не требуется.

> Реализационно: нужно встроить «отправку на измерение» в маршрут между этапами.
> Варианты — отдельная очередь измерения перед каждым этапом, или флаг на партии
> «нужно измерить после стадии X». Выбери чистый способ, согласованный с текущим
> механизмом очередей. Главное: измерение занимает M-GMM и время, и партия не
> уходит на следующий этап, пока не измерена (см. раздел 8 — hold).

## 8. Hold: партия не уходит дальше до измерения (production.py, domain/batch.py)

Сейчас баг-гонка: партия кладётся в следующую очередь И ставится spot-check
одновременно → production может схватить её раньше, чем quality измерит.

Добавить флаг `Batch.quality_hold: bool`. Когда этап закончен и партия
отправлена на измерение → `quality_hold=True`. `production._assign_from_queue`
**пропускает** партии с `quality_hold=True` (не назначает на станок). Quality,
завершив измерение → `quality_hold=False`. На следующем тике партия свободна для
следующего этапа.

## 9. SQL-таблица measurements (postgres/init/init.sql + services/quality/main.py)

Добавить ОДНУ таблицу (для удобных Grafana-дашбордов; ML по-прежнему ест логи).
Каждое измерение пишется И в логи (как сейчас), И в эту таблицу.

```sql
CREATE TABLE measurements (
    measurement_id    BIGSERIAL   PRIMARY KEY,
    batch_id          TEXT        NOT NULL,
    part_index        INTEGER     NOT NULL,
    product_code      TEXT        NOT NULL,
    stage             TEXT        NOT NULL,
    machine_id        TEXT        NOT NULL,   -- где обрабатывалась деталь
    parameter         TEXT        NOT NULL,
    value             REAL        NOT NULL,
    nominal           REAL        NOT NULL,
    tolerance         REAL        NOT NULL,
    unit              TEXT        NOT NULL,
    result            TEXT        NOT NULL,   -- pass | fail
    reason            TEXT,                   -- причина при fail; NULL при pass
    source_machine_id TEXT,                   -- станок-виновник; NULL при фоне/pass
    scenario_id       TEXT,                   -- id сценария; NULL иначе
    measured_at       TIMESTAMP   NOT NULL
);
```

Одна строка = одно измерение одного параметра одной детали (длинный формат —
удобен для Grafana GROUP BY). В `services/quality/main.py` расширить Pydantic
`Measurement` новыми полями и добавить INSERT в `measurements` (сейчас там
«measurement только в логи» — добавить запись в БД, лог оставить). Симулятор
(`client.measurement` + `quality._measure_part`) должен передавать новые поля
(stage, part_index, product_code, result, reason, source_machine_id, scenario_id,
machine_id). Сейчас `client.measurement` шлёт меньше полей — расширить сигнатуру.

Таблицы `batch_defects` и `scenario_log` НЕ создавать (дефекты =
`measurements WHERE result='fail'`, сценарии видны в логах).

## 12. Логирование (для ML — приоритет)

Всё, что важно для ML, должно осесть в **логах** (JSON). Убедись, что в логи
попадают: каждое измерение (с parameter/value/result/reason/source_machine_id/
scenario_id/stage), каждый запуск и конец сценария (machine_id, scenario_type,
severity, parts_limit, время), каждый WO и смена состояния станка. Лог — сырьё
для ML; таблица `measurements` — витрина для Grafana. Дублирование измерений в
оба места — намеренное.
