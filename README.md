# Интеллектуальная система мониторинга и предиктивного анализа логов

Это проект к моей выпускной квалификационной работе. Если коротко — здесь собран небольшой «завод» по производству зубчатых колёс, который полностью живёт в контейнерах, пишет логи как настоящая микросервисная система, а поверх этих логов работает машинное обучение: оно ловит аномалии в технологическом процессе и заранее предупреждает о тех, что только начинают развиваться. Плюс есть мониторинг в Grafana, где видно текущее состояние всего участка.

Завода у нас, понятно, нет, поэтому его роль играет **симулятор**. Он ведёт себя как реальное производство: запускает заказы, гоняет детали по станкам, топит печь, меряет качество и время от времени «ломается» по заданным сценариям. А дальше всё как на настоящем заводе — сервисы пишут логи, логи собираются, ML их анализирует, Grafana показывает картину.

## Из чего всё состоит

Система — это набор сервисов, каждый в своём контейнере:

| Сервис | Порт | Что делает |
|--------|------|------------|
| `equipment` | 8001 | оборудование, цеховая телеметрия (роль SCADA) |
| `production` | 8002 | управление производством, заказы и партии (роль MES) |
| `quality` | 8003 | контроль качества деталей (роль QMS/SPC) |
| `maintenance` | 8004 | техобслуживание и ремонты (роль CMMS/EAM) |
| `simulator` | 8005 | сам «завод» + панель управления им |
| `ml` | 8006 | анализ: детекция аномалий и прогноз (Prophet) + своя панель |
| `grafana` | 3000 | дашборды мониторинга |
| `loki` | 3100 | хранилище логов |
| `promtail` | — | собирает логи из контейнеров и отдаёт в Loki |
| `postgres` | 5432 | база данных (производство + результаты анализа) |

Поток данных простой: симулятор дёргает бизнес-сервисы → те пишут структурированные JSON-логи → Promtail складывает их в Loki → ML-сервис читает логи из Loki, считает аномалии и прогнозы, пишет результат в Postgres → Grafana всё это показывает.

## Что нужно для запуска

Только **Docker** и **Docker Compose** (v2). Больше ничего ставить не надо — ни Python, ни библиотеки, всё уже внутри образов.

```bash
git clone https://github.com/M-A-L-I-K-05/log-monitoring.git
cd log-monitoring
docker compose up -d --build
```

Первая сборка занимает несколько минут (тянутся образы и ставятся ML-библиотеки). После этого проверить, что всё поднялось:

```bash
docker compose ps
```

Все сервисы должны быть в состоянии `running`. База данных создаёт таблицы сама при первом старте.

## Куда заходить

Открывать в браузере:

- **Симулятор (панель управления заводом)** — http://localhost:8005
- **ML-сервис (панель анализа)** — http://localhost:8006
- **Grafana (мониторинг)** — http://localhost:3000 (логин не нужен, вход анонимный с правами админа)

## Как всё запустить и посмотреть в работе

Порядок такой: сначала «оживляем» завод, даём ему поработать в норме, потом обучаем на этой норме модели, включаем анализ — и смотрим.

### 1. Запускаем завод

Заходим в панель симулятора (http://localhost:8005) и нажимаем **Start**. Дальше включаем:

- **автозаказы** — чтобы на участок постоянно поступала работа и станки не простаивали;
- **скорость** — можно ускорить модельное время (например, в 100 раз), чтобы не ждать часами; печь и износ инструмента — процессы медленные, на ускорении статистика набирается быстро.

Можно и без панели, через API:

```bash
curl -X POST http://localhost:8005/start
curl -X POST http://localhost:8005/orders/auto -H "Content-Type: application/json" -d '{"enabled": true}'
curl -X POST http://localhost:8005/speed       -H "Content-Type: application/json" -d '{"multiplier": 100}'
```

Дайте заводу поработать несколько минут «в норме» (без аномалий) — чтобы накопились нормальные показания, на которых будут учиться модели.

### 2. Обучаем модели

Анализ работает по принципу «сначала покажи, как выглядит норма». Поэтому модели надо обучить на нормальных данных. Заходим в панель ML (http://localhost:8006) и жмём **Train** (обучить). Веса сохраняются и переживают перезапуск контейнера (лежат в отдельном volume).

Через API то же самое:

```bash
curl -X POST http://localhost:8006/train
curl http://localhost:8006/models            # посмотреть список обученных версий
```

Обучается отдельная норма под каждый тип станка и тип детали — так точнее, чем «одна норма на всё».

### 3. Включаем анализ

Два контура включаются независимо:

- **Детекция** — ловит уже наступившие отклонения (сочетание z-оценки, ECOD, Isolation Forest и правила «отклонение держится несколько отсчётов подряд»).
- **Прогноз (Prophet)** — смотрит на тренд и предупреждает о выходе за норму заранее.

В панели ML включаем оба переключателя. Через API:

```bash
curl -X POST http://localhost:8006/loop         -H "Content-Type: application/json" -d '{"enabled": true}'
curl -X POST http://localhost:8006/prophet_loop -H "Content-Type: application/json" -d '{"enabled": true}'
```

Теперь анализ работает в фоне сам: детекция — каждые несколько секунд, прогноз — чуть реже.

### 4. Устраиваем аномалию

Чтобы увидеть, как система реагирует, можно запустить поломку. Либо включить **автосценарии** (симулятор сам будет периодически запускать разные аномалии на случайных станках), либо запустить конкретный сценарий вручную из панели симулятора.

Через API — автосценарии:

```bash
curl -X POST http://localhost:8005/scenarios/auto -H "Content-Type: application/json" -d '{"enabled": true}'
```

Сценарии бывают резкие (вибрация, ослабление заготовки, потеря охлаждения, прижоги при шлифовании) и медленные, дрейфовые (износ инструмента, фрезы, шевера, недо-/перецементация в печи). Дрейфовые как раз интересны прогнозом — их Prophet успевает «увидеть» заранее.

### 5. Смотрим в Grafana

Открываем http://localhost:3000. Там три готовых дашборда (создаются автоматически):

- **ML Detection** — найденные аномалии: какой станок, какой датчик, когда. Тут видно работу контура детекции.
- **ML Prophet** — карточки прогноза: где показания приближаются к границе нормы и где Prophet поднял предупреждение.
- **Quality / Scenarios** — состояние производства и качество: ход партий, причины брака по сценариям. Это и есть «вид на завод сверху», которого в жизни нет, а здесь всё на одном экране.

### 6. Оцениваем качество (по желанию)

В панели ML есть кнопка **Evaluate** — она сверяет, какие из запущенных сценариев система действительно поймала, и считает метрики (полнота, точность, упреждение). Удобно, чтобы проверить, насколько хорошо всё работает.

```bash
curl -X POST http://localhost:8006/evaluate
```

## Полезные команды

Сброс результатов анализа (чистит таблицы ML, веса моделей не трогает):

```bash
curl -X POST http://localhost:8006/reset
```

Остановить всё:

```bash
docker compose down
```

Остановить и стереть данные (база, логи, дашборды — всё с нуля при следующем старте):

```bash
docker compose down -v
```

> Осторожно с `-v`: это удаляет тома, то есть базу, накопленные логи и обученные модели. После такого надо будет заново дать заводу поработать в норме и переобучить модели.

## Структура репозитория

```
services/        четыре бизнес-сервиса (equipment, production, quality, maintenance)
simulator/       симулятор завода + веб-панель управления
ml/              ML-сервис: детекция, прогноз, веб-панель
grafana/         провижининг дашбордов и источников данных
loki/            конфигурация Loki
promtail/        конфигурация сбора логов
postgres/        init-скрипты базы (создание таблиц)
docker-compose.yml
Final qualifying work/   текст пояснительной записки ВКР
```

## Пара слов напоследок

Проект делался как учебный, в рамках диплома, но это не макет на бумаге — всё реально запускается и работает целиком, от генерации логов до анализа и дашбордов. Аналитическое ядро не привязано жёстко к зубчатым колёсам: всё про конкретное производство вынесено в настройки, так что при желании ту же схему можно навести и на другой процесс — подключить реальный поток логов вместо симулятора и переобучить модели на его норме.
