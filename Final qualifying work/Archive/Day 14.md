## 1. Две шкалы дисперсии: сырая 15-секундная и минутная

Это фундамент всех дальнейших выводов. Везде ниже — **чистая статистика, без привязки к коду**.

### 1.1 Модель шума

Одно сырое показание сенсора внутри минуты:
```
x_i = μ + ε_i ,   ε_i ~ N(0, σ_raw²) ,   i = 1..n ,   ε_i независимы (i.i.d.)
```
где `μ` — стационарное среднее сенсора, `σ_raw` — его «сырая» σ (та, что хранит детектор), а
```
n = T_min / T_raw = 60 с / 15 с = 4
```
— число сырых показаний в одной минуте.

### 1.2 Минутное среднее: центр инвариантен, разброс падает в √n

Ресемпл «1 минута, mean» — это выборочное среднее `n` показаний:
```
x̄ = (1/n) Σ x_i = μ + (1/n) Σ ε_i
```

Математическое ожидание (центр) **не меняется**:
```
E[x̄] = μ
```

Дисперсия среднего независимых слагаемых:
```
Var(x̄) = (1/n²) · Σ Var(ε_i) = (1/n²) · n·σ_raw² = σ_raw² / n
⇒  σ_min = σ_raw / √n = σ_raw / 2          (n = 4)
```

**Вывод (запомнить для записки):** усреднение до минуты **сохраняет центр** `μ` и **сжимает шум в √n = 2 раза**. Это не свойство кода, а свойство среднего i.i.d.-величин.

### 1.3 Условие применимости √n

Множитель ровно `√n` верен **только при независимости** `ε_i`. В симуляторе каждое показание — самостоятельный розыгрыш `bounded_gauss(mean, std)`, поэтому независимость выполняется точно. Для реального датчика с автокорреляцией шума эффективное число независимых отсчётов `n_eff < n`, и сжатие было бы слабее (`σ_raw/√n_eff`). Это честная оговорка для защиты: на синтетике коэффициент точен, на реальных данных — верхняя оценка эффекта.

## 2. Чувствительность к сдвигу: детектор (сырая σ) vs Prophet (минутная σ)

Ключевой результат дня. Обе системы сравнивают **минутную величину**, но **с разными линейками**:
- детектор — с **сырой** `σ_raw` (намеренно, демпинг шума, см. Day 13 §3);
- Prophet — с **минутной** `σ_min` (после фикса полосы, Day 13 §7).

Из-за этого пороги, выраженные в физических единицах сенсора, различаются вдвое.

### 2.1 Детектор: при каком сдвиге срабатывает

Скоринг идёт по минутному среднему `x̄`, сравнивается с сырой σ:
```
z_det = (x̄ − μ) / σ_raw
```
Разложим `x̄ = μ + Δ + шум`, где `Δ` — устойчивый сдвиг среднего (от сценария):
- вклад шума:  `std = σ_min/σ_raw = 1/√n = 0.5`  (тих, до порога не доводит);
- вклад сдвига: `E[z_det] = Δ / σ_raw`.

Порог `Z = ANOMALY_Z = 2.8`. Срабатывание (сдвиг доминирует над шумом 0.5):
```
|z_det| ≥ Z   ⇔   Δ ≳ Z · σ_raw = 2.8 · σ_raw
```

### 2.2 Prophet: при каком сдвиге срабатывает

Полоса нормы (после фикса) — в минутной σ:
```
нижняя/верхняя = μ ∓ Z · σ_min = μ ∓ Z · σ_raw/√n = μ ∓ 1.4 · σ_raw
```
На плато сдвига прогноз `yhat → μ + Δ`. Пробой:
```
|yhat − μ| ≥ Z · σ_min   ⇔   Δ ≥ Z · σ_raw/√n = 1.4 · σ_raw
```

### 2.3 Отношение чувствительностей

```
R = Δ_крит(детектор) / Δ_крит(Prophet) = (Z·σ_raw) / (Z·σ_min) = √n = 2
```

**Результат:** к устойчивому сдвигу среднего **Prophet ровно в √n = 2 раза чувствительнее** детектора — он пробивает полосу при половинном сдвиге (`1.4 σ_raw` против `2.8 σ_raw`). Причина чисто математическая: оба меряют один и тот же минутный уровень, но Prophet — против узкой (минутной) линейки, детектор — против широкой (сырой).

| система | линейка | критический сдвиг |
|---|---|---|
| детектор (z-правило) | `σ_raw` | `2.8 σ_raw` |
| Prophet (полоса) | `σ_min = σ_raw/2` | `1.4 σ_raw` |

## 3. Почему **step-сценарий** первым поймал Prophet (коррекция гипотезы Day 13)

Ранее (Day 13, устно) предполагалось: на резкой ступеньке детектор всегда быстрее, Prophet — для плавных трендов. Практика опровергла: `quench_distortion` (step, калибровка 3σ_raw при light, Day 13 §6.2) первым отметил Prophet. Разбор показал **три независимых математических причины**, и все играют за Prophet:

**(а) Узкая полоса (раздел 2).** Ступенька выходит на плато `Δ_step ≈ 3 σ_raw`. Детектору нужен `2.8 σ_raw`, Prophet'у — `1.4 σ_raw`. Пока минутный уровень только набирается к плато, он раньше пересекает порог Prophet'а.

**(б) Экстраполяция тренда на горизонт.** Prophet оценивает локальный наклон `s` (на минуту) по последним точкам и прогнозирует на горизонт `H = 30` мин:
```
yhat(t+H) ≈ уровень(t) + s · H
```
Свежая ступенька выглядит как крутой changepoint: даже при ещё не достигнутом плато наклон `s` велик, и `s·H` выносит `yhat` далеко за полосу. Детектор смотрит **только на текущее значение**, без заглядывания вперёд.

**(в) Нет фильтра персистентности.** Детектор пишет аномалию лишь после `PERSIST_N = 3` подряд «горячих» точек канала (Day 13 §1) — это добавляет латентность `(PERSIST_N − 1)` скоринговых точек. Prophet пишет статус по **одному** циклу, как только прогноз пробил полосу (`n_breaches > 0`).

**Итог для записки:** «step → детектор быстрее» — неверное упрощение. Усреднение делает полосу Prophet вдвое уже (а), горизонтальная экстраполяция срабатывает ещё до выхода на плато (б), отсутствие персистентности убирает стартовую задержку (в). Поэтому на умеренных по сырой шкале ступеньках **раньше реагирует именно предиктивный контур**. Детектор и Prophet остаются взаимодополняющими, но граница «тренд/ступенька» между ними — не резкая.

## 4. Непрерывный синтетический минутный индекс (метод сбора истории)

**Задача.** Кормить Prophet **накопленной историей** комбинации (станок, контекст) через прошлые циклы/партии, игнорируя дыры реального времени (печь в idle, смена фазы, перемотка), и при этом **не разрушить дисперсию** (ловушка `ffill` из Day 13 §2, но теперь для истории прогноза).

**Метод.**
1. Берём все показания контекста: для печи — по фазе (`carburizing`/`quenching`), для станков — по `product_code`.
2. Ресемпл в минуты средним, **пустые корзины выбрасываем** (`dropna`), **НЕ `ffill`**.
3. Уцелевшие минутные значения кладём на **последовательную синтетическую минутную ось** (`date_range`, шаг 1 мин), сохраняя порядок и **отбрасывая реальные метки времени**.
4. Обрезаем до последних `PROPHET_SERIES_POINTS = 200` точек.

**Почему `dropna`, а не `ffill` (математика).** `dropna` сохраняет эмпирическую σ реальных показаний. `ffill` через часовой простой вставил бы десятки одинаковых значений → дисперсия схлопывается (`σ → 0`) → полоса нормы занижается, а тренд становится искусственно плоским. Синтетическая ось чинит **только** предположение Prophet о равномерном шаге `ds`; она **не выдумывает значений** — все точки реальны, меняется лишь подпись времени.

**Cold-start guard.** Порог `PROPHET_MIN_POINTS = 60` минутных точек (Day 13 §7.1) остаётся, но теперь это **только нижний предохранитель** для самого старта, когда истории почти нет, — а не оценка «текущего этапа». В норме история контекста за прошлые партии даёт ≥ 200 точек.

**Принцип для записки:** растягивание разрывного по времени ряда на непрерывную ось допустимо, если (1) переносятся реальные значения без интерполяции и (2) сама модель не использует абсолютное время (сезонность у Prophet отключена). Иначе появляются фантомные тренды.

## 5. Синхронный бюджет прогнозного цикла (производительность)

Прогнозный контур и детекция делят **один фоновый поток**, поэтому время цикла Prophet — это пауза детекции. Стоимость цикла:
```
C = t_fetch + t_parse + Σ_s t_fit(s) ≈ t_fetch + N · t̄_fit
```
где `N` — число проверяемых сенсоров (= число фитов Prophet), `t̄_fit` — среднее время одного фита.

**Замеры (симулятор ×1000, заполненный Loki):**
- `t_fetch ≈ 5.7 с` — один bulk-запрос 40 000 строк (8 страниц × 5000); `t_parse + frames ≈ 0.4 с`. **Не зависит от `N`.**
- `t̄_fit ≈ 0.11 с/сенсор` (медиана; диапазон 0.056–0.39).
- `N` при одном активном контексте на станок (14 станков) `≈ 43` ⇒ `Σ t_fit ≈ 4.7 с`.
- `C ≈ 10.8 с` — реалистичный худший случай.
- Контрольный бенчмарк по **всем** контекстам сразу (`N = 83`, удвоенный счёт шестерён) дал `17.9 с` — заведомо завышенная верхняя граница.

**Вывод:** доминирует **`t_fetch` (чтение Loki), а не фиты Prophet**. Фиты масштабируются линейно по `N` (~0.1 с каждый — дёшево), а выгрузка почти постоянна (всегда последние 40 000 строк, ~6 с) и от `N` и от объёма Loki не зависит.

## 6. Выбор периода прогнозного цикла

Период `P` обязан удовлетворять `P > C_худш`, иначе циклы наслаиваются и детекция голодает (наблюдалось как «зависание run_count», лечилось переходом на bulk-выгрузку).
```
C_худш ≈ 11 с  ⇒  P = 15 с  (запас ≈ 4 с, P ≈ 1.4·C)
```
Снижено с 30 с до 15 с: карточки Grafana обновляются вдвое чаще, поток успевает вернуться к детекции до следующего запуска. При `BACKGROUND_INTERVAL = 5 с` это `prophet_every = P/interval = 3` тика.

**Принцип для записки:** период синхронного фонового контура выбирается от **измеренного** худшего времени цикла с запасом (~40 %), а не «на глаз». Узкое место определяет, что оптимизировать (здесь — выгрузка из Loki, не модель).

## 7. Остаточная ложная аномалия Prophet на quenching: диагноз и фикс окном

**Симптом.** При фоновой работе изредка мигает ложная карточка **только по печи, только `furnace_temp_zone1` в фазе quenching**: `n_breaches = 2`, `lead ≈ 29` мин, `yhat_end ≈ 836` ровно на нижней границе нормы `[836, 850]`. Карточка через цикл гаснет (PK `ml_prophet_status` = (machine_id, sensor) без контекста; `zone1` входит и в carburizing, и в quenching → строка перезаписывается нормой текущей фазы).

**Это не регресс фиксов Day 13, а их «слепая зона».** Замер длины окна по контекстам:

| контекст | минутных точек (bulk 40000) | yhat-наклон на горизонте | хвост прогноза vs норма |
|---|---|---|---|
| carburizing (обе печи) | **200** (потолок) | ≈ 0 (±0.01/мин) | глубоко внутри |
| quenching M-FRN-01 | 83 | −0.04/мин | внутри |
| quenching **M-FRN-02** | **58** (на полу `PROPHET_MIN_POINTS=60`) | **−0.15/мин** | **задевает 836** |

**Корень — длина окна, не логика Prophet.** Quenching — **короткая фаза**, поэтому даже при сборе по всем партиям (раздел 4) в bulk-окно влезает лишь ~58 минутных точек против 200 у длинного carburizing. На коротком ряду кусочно-линейный тренд Prophet цепляется за **последний шумовой сегмент**: истинный наклон ≈0, а экстраполируемый — −0.15/мин (×8). За горизонт 30 мин это −4.5 единицы; стартуя от среднего 843, хвост падает на 836 = нижняя норма (полоса узкая, ±7 = ±2.8σ при σ≈2.5). Когда шумовой наклон случайно вниз — мигает; вверх — нет. carburizing не мигает: при 200 точках наклон стабильно ≈0.

**Почему не трогаем `changepoint_prior_scale`.** Демпфирование тренда Prophet убрало бы экстраполяцию, но **глобально** изменило бы поведение и на step-сценариях (раздел 3), которые работают как надо. Лечим причину (длину окна), а не модель.

**Фикс — увеличить окно сбора, `PROPHET_BULK_FETCH = 40000 → 80000`.** Замер зависимости (quenching M-FRN-02):

| bulk | время fetch* | quench точек | yhat-наклон | хвост |
|---|---|---|---|---|
| 40000 | 2.2 с | 58 | −0.15/мин | 836.6 (=граница) |
| **80000** | 3.5 с | **~135** | **−0.02/мин** | 841.5 (запас +5.5) |
| 120000 | 6.0 с | 200 | −0.03/мин | 841.2 |

\* при лёгкой нагрузке; под пиком ×~2.6.

Выбрано **80000** (а не 120000): quenching выходит на ~116–135 точек, наклон выпрямляется −0.15 → −0.02/мин, запас до нормы +5σ — ложная уходит, при этом период цикла **остаётся 15 с** (реальный цикл после фикса 8.0 с, аномалий 0, детекция тикает). 120000 дал бы полный паритет (200 точек), но цикл ~17–20 с потребовал бы периода 30 с — лишняя цена за уже решённую проблему.

**Принцип для записки:** у коротких регламентных фаз окно прогноза лимитировано не методом сбора, а **их долей в потоке** — короткая фаза набирает точки медленно. Лекарство — расширять историческое окно (дешёвый bulk-запрос по меткам), а не «чинить» экстраполятор. Узкое место снова — данные, не модель.
