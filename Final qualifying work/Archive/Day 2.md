## Что сделано

### 1. Окружение и инструменты

- В корне `~/projects/vkr-log-monitoring/` создано venv: `python3 -m venv .venv`
- Установлены пакеты: `fastapi`, `uvicorn`, `python-json-logger`, `pydantic`
- venv нужен только для локальной разработки — в Docker зависимости ставятся напрямую в системный Python контейнера

### 2. Структура сервисов

В каждой папке `services/<service-name>/` теперь лежат:

```
services/equipment/
├── main.py          # FastAPI-приложение
├── requirements.txt # зависимости
└── Dockerfile       # инструкции сборки образа
```

Все четыре сервиса структурно одинаковы: функция `setup_logging`, инициализация `app`, набор Pydantic-моделей, набор POST-эндпоинтов.

### 3. JSON-логирование

Реализована функция `setup_logging(service_name)`, которая:

1. Создаёт `JsonFormatter` с переименованием полей (`asctime` → `timestamp`, `levelname` → `level`)
2. Подключает `StreamHandler` к корневому логгеру (`root.handlers.clear()` + `root.addHandler`)
3. Очищает handler'ы у логгеров `uvicorn`, `uvicorn.error`, `uvicorn.access` и включает `propagate = True`
4. Возвращает именованный логгер сервиса

**Итог:** все логи в процессе (свои + uvicorn + FastAPI) идут единым JSON-форматом.

**Унифицированная схема бизнес-события:**

```json
{
  "timestamp": "...",
  "level": "INFO",
  "name": "equipment",
  "message": "sensor_reading",
  "event": "sensor_reading",
  "entity_id": "M03",
  "details": { ... }
}
```

Верхний уровень — метаданные. Поле `details` — специфика конкретного события. ML-сервис потом будет рассчитывать на эту структуру.

### 4. Эндпоинты по сервисам

Все пути — существительные-события. Все методы POST (кроме `/health`).

**Equipment Service (порт 8001, SCADA):**

- `POST /sensor-reading` — показания датчиков (температура, вибрация)
- `POST /state-change` — смена состояния станка
- `POST /alarm` — авария
- `POST /cycle-completion` — завершение производственного цикла

**Production Service (порт 8002, MES):**

- `POST /order-creation` — создан заказ
- `POST /batch-start` — запуск партии
- `POST /batch-completion` — завершение партии
- `POST /batch-move` — передача партии на следующий участок

**Quality Service (порт 8003, QMS):**

- `POST /measurement` — замер детали
- `POST /inspection-result` — результат контроля
- `POST /spc-violation` — нарушение SPC

**Maintenance Service (порт 8004, CMMS):**

- `POST /work-order-creation` — создан наряд
- `POST /work-order-assignment` — наряд назначен бригаде
- `POST /work-order-completion` — наряд закрыт
- `POST /scheduled-maintenance` — выполнено плановое ТО

### 5. Контейнеризация

Единый шаблон Dockerfile, отличается только порт:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

Принципы:

- `requirements.txt` копируется отдельно от кода → правильный layer caching (изменение кода не пересобирает зависимости)
- `--host 0.0.0.0` обязательно: внутри контейнера нужно слушать на всех интерфейсах
- `CMD` в exec form
- `python:3.12-slim` базовый образ — общий слой для всех сервисов, скачивается один раз

### 6. Проверка

Каждый образ собран командой `docker build -t <service>-service:dev .`. Запущен через `docker run --rm -p <port>:<port>`. Проверен через `curl /health` — все четыре отвечают своим именем сервиса. В логах JSON-формат подтверждён.

## Ключевые концепции для запоминания

### FastAPI + uvicorn + ASGI

- **FastAPI** — библиотека для написания HTTP-приложений, не сервер
- **uvicorn** — ASGI-сервер, который слушает порт и вызывает приложение
- **ASGI** — стандарт интерфейса между сервером и приложением: `app(scope, receive, send)`
- `app` — экземпляр класса FastAPI, у которого есть `__call__` — поэтому uvicorn может вызывать его как функцию
- Команда `uvicorn main:app` — это «импортировать модуль `main`, взять оттуда переменную `app`»
- При импорте модуля выполняется код верхнего уровня → срабатывают декораторы `@app.get()`, `@app.post()` → функции регистрируются в `app.routes`
- Каждый запрос → uvicorn парсит HTTP → вызывает `app(...)` → FastAPI смотрит маршрутную таблицу → вызывает нужную функцию

### Pydantic и валидация

- Pydantic-модель = класс с type hints, описывающий структуру данных
- FastAPI видит type hint `data: SensorReading` → понимает «брать из тела запроса, валидировать через эту модель»
- При невалидных данных FastAPI автоматически возвращает HTTP 422
- `field: str | None = None` — необязательное поле со значением по умолчанию
- На каждый запрос создаётся **новый экземпляр** модели — это нормально, Pydantic v2 на Rust, очень быстрый

### Иерархия логгеров Python

- Логгеры образуют **дерево**, корень — root logger
- Имена логгеров с точкой задают иерархию: `uvicorn.access` дочерний к `uvicorn`, тот — к root
- **Propagation**: сообщение всплывает к родителю → если `propagate=True`, проходит через handler'ы всех родителей вплоть до root
- Поэтому настройка одного handler'а на root → весь Python-процесс пишет в этом формате
- `uvicorn` по умолчанию ставит свои handler'ы и `propagate=False` → его логи не идут через root → нужно явно очистить и включить propagation
- Первые 3 сообщения uvicorn (до импорта main.py) всё равно идут в обычном тексте — это нормально

### Docker, образы, контейнеры

- **Образ** — шаблон, по которому создаются контейнеры
- **Контейнер** — запущенный экземпляр образа
- **Слой (layer)** — каждая инструкция в Dockerfile создаёт слой; Docker кеширует и переиспользует
- **`COPY` vs bind mount**: COPY включает файлы в образ (production), bind mount подменяет содержимое директории на лету (разработка, через docker-compose)
- `WORKDIR /app` — задаёт рабочую директорию контейнера, дальше всё относительно неё
- `EXPOSE` — информационная инструкция, не открывает порт; реальный проброс делается через `-p` или в compose
- `--host 0.0.0.0` нужно потому, что 127.0.0.1 контейнера != 127.0.0.1 хоста
- Имя:тег образа (`equipment-service:dev`) — `:dev` это просто строка-метка, не магия

### Сеть Docker и общение между контейнерами

- Docker Compose создаёт виртуальную сеть для всех сервисов
- Каждый сервис доступен по **имени сервиса в compose** через встроенный DNS
- Из одного контейнера в другой: `http://equipment:8001/...` (не localhost, не IP — имя сервиса)
- Имя образа, имя контейнера и имя сервиса — разные вещи; для общения используется именно имя сервиса

## Шероховатости и компромиссы

- Поля `message` и `event` в логах дублируют значение. Сделано осознанно: `event` — точка опоры для LogQL и ML, не пересекается со стандартным `message` от библиотек
- Первые сообщения uvicorn печатаются обычным текстом до выполнения `setup_logging` — нормально, не критично
- Сервисы пока возвращают только подтверждение приёма, без обращения к БД и без бизнес-логики — это правильное состояние для дня 2
