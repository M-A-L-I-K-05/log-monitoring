# Логика ML-сервиса и оценки: что, откуда и куда

Документ-объяснение (не текст ПЗ). Цель — снять путаницу: что делает интеллектуальная модель, что делает оценка, и почему это РАЗНЫЕ вещи. Всё сверено с реальной БД и кодом.

## Главная мысль (читать первой)

В системе ДВА независимых конвейера:

1. **Интеллектуальный анализ** (детектор + Prophet) — работает ВСЛЕПУЮ. Вход — только сырые показания датчиков (`sensor_reading`). Он НЕ знает про сценарии, НЕ читает таблицу сценариев. Просто видит числа с датчиков и решает: «аномалия / прогноз выходит за норму».

2. **Оценка качества** (`/evaluate`, только для главы 4) — это «проверяющий». Он берёт сценарии как ПРАВИЛЬНЫЕ ОТВЕТЫ (мы сами их запускали и знаем, где/когда) и сравнивает с тем, что выдала модель в конвейере 1. Оценка НЕ влияет на модель и НЕ участвует в детекции.

Поэтому никакой циркулярности нет: модель не подсматривает ответы. Логи сценариев — это тестовый артефакт (разметка), как контрольная с заранее известными ответами. В реальном заводе сценариев нет — модель работает так же на сырых данных, просто без сценариев нельзя автоматически посчитать precision/recall (нет эталона).

## Сколько таблиц и что каждая делает

Всего 11 таблиц: 5 заводских (создаёт `postgres/init/init.sql`) + 6 ML (создаёт сам ML-сервис в `ml/store.py`).

### Заводские (пишут доменные микросервисы из событий симулятора)

| Таблица | Что хранит | Кто пишет | Кто читает |
|---|---|---|---|
| machines | справочник парка станков | equipment (по Sync Fleet) | Grafana, переменная $machine |
| machine_status | текущее состояние станков | equipment | Grafana (завод) |
| active_batches | активные партии в работе | production | Grafana (завод) |
| open_work_orders | открытые наряды на ТО | maintenance | Grafana (завод) |
| measurements | измерения качества деталей | quality | Grafana (завод) |

Эти таблицы к ML-анализу и к оценке отношения почти не имеют — это «бизнес-витрина» завода.

### ML (пишет ML-сервис)

| Таблица | Что хранит | Кто пишет | Кто читает |
|---|---|---|---|
| ml_runs | журнал прогонов ML (служебный) | pipeline | Detection-дашборд (счётчик) |
| ml_anomalies | ВЫХОД ДЕТЕКТОРА: все оценённые точки с флагом is_anomaly | run_once (по sensor_reading) | Detection-дашборд + /evaluate |
| ml_forecasts | ряд прогноза Prophet (рудимент, дашборды не читают) | run_prophet_cycle | — |
| ml_prophet_status | витрина-СНИМОК Prophet для карточек Grafana (перезаписывается, TTL-чистка) | run_prophet_cycle (upsert) | Prophet-дашборд |
| ml_prophet_events | append-only ИСТОРИЯ предупреждений Prophet (без жизненного цикла: нашёл — записал) | run_prophet_cycle (на фронте false to true) | /evaluate |
| ml_scenarios | GROUND TRUTH: окна запущенных сценариев (машина, старт, конец) | /evaluate (_sync_scenarios из логов scenario_event) | /evaluate |

## Конвейер 1: интеллектуальный анализ (слепой)

Источник данных — только логи `sensor_reading` в Loki (сырые показания датчиков, их пишет equipment-сервис).

- ДЕТЕКТОР (`run_once`): тянет `sensor_reading` из Loki, прогоняет через ECOD/IsolationForest/z-score с персистентностью, пишет результат в `ml_anomalies` (каждая точка + флаг is_anomaly). Про сценарии не знает ничего.
- PROPHET (`run_prophet_cycle`): тянет `sensor_reading` из Loki, строит прогноз на горизонт, проверяет выход за норму. Пишет:
  - `ml_prophet_status` — текущий снимок для карточек Grafana (одна строка на станок-сенсор, перезаписывается, чистится по TTL);
  - `ml_prophet_events` — append-only лог: когда впервые на станок-сенсоре прогноз вышел за норму (фронт нарастания), с упреждением lead_min. Эту таблицу НЕ чистит TTL — она и есть история поимок.

Ни детектор, ни Prophet НЕ читают `scenario_event` и `ml_scenarios`.

## Конвейер 2: оценка (/evaluate) — проверяющий

Единственное место, где вообще используются сценарии. Шаги:

1. Читает логи `scenario_event` из Loki (их пишет quality-сервис, когда МЫ запускаем сценарий — это разметка «здесь мы намеренно сломали станок X в момент T»). Складывает окна в таблицу `ml_scenarios` (машина, старт, конец).
2. Берёт выход модели, уже посчитанный вслепую: срабатывания детектора из `ml_anomalies`, предупреждения Prophet из `ml_prophet_events`.
3. СВЕРЯЕТ по машине и времени: для каждого окна сценария (машина M, интервал [старт, конец]) проверяет —
   - есть ли срабатывание детектора на машине M внутри окна → детектор «поймал», задержка = первое_срабатывание − старт;
   - есть ли предупреждение Prophet на машине M внутри окна → Prophet «поймал», упреждение = lead_min.
4. Срабатывания ВНЕ всех окон сценариев считаются ложными (FP). Из этого — precision; из доли пойманных сценариев — recall.

Результат `/evaluate` — единый JSON с раздельными секциями detector и prophet + разбор по каждому сценарию (корреляция по названию сценария). Это и есть таблица для главы 4.

## Про окно сценария (важная деталь матчинга)

Лог сценария помечает старт (машина + время). Конец — если есть событие завершения (`auto_completed`/`stopped`). Если завершения нет (сценарий «открыт», в логах только start — типично для печи, где искажение проявляется через часы, когда загрузка входит в фазу цементации): окно тянем до конца данных прогона. Обоснование: на станке в один момент активен только один сценарий, поэтому любое срабатывание на этой машине после старта относится именно к нему — включая раннее предиктивное предупреждение Prophet ещё ДО того, как дрейф достиг порога (это корректная ранняя поимка, а не ложное срабатывание).

## Зачем тогда логи сценариев, если «модель умная»

Логи сценариев нужны ТОЛЬКО для проверки качества (глава 4). Это эталон ответов. Модель их не видит и работает на сырых датчиках. Убери разметку сценариев — детекция и прогноз работают точно так же, просто нельзя автоматически измерить точность (не с чем сравнивать). Поэтому интеллектуальность модели сохраняется полностью: она находит аномалии сама, а сценарии лишь позволяют посчитать, насколько хорошо она это делает.
