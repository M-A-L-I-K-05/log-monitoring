3.6. Реализация хранения и витрин результатов

Хранение результатов анализа реализовано отдельным модулем, который служит для ML-сервиса единой точкой доступа к базе данных PostgreSQL [29]. Соединения с базой берутся из пула, что позволяет повторно использовать установленные подключения и не открывать новое на каждый запрос. При запуске сервиса модуль приводит схему таблиц результатов к актуальному виду: таблицы создаются идемпотентно, по условию их отсутствия, а для ранее созданных баз применяются мягкие миграции - добавление недостающих столбцов выполняется только при их отсутствии, что делает повторный запуск безопасным. Схема таблиц результатов приведена в листинге Г.7. При этом производственные таблицы модуль не затрагивает: их схема задаётся отдельно и наполняется бизнес-сервисами (раздел 2.6), а ML-сервис ведёт только собственные таблицы результатов.

Результаты контура детекции записываются пакетно. Обработанные за прогон точки заносятся в таблицу аномалий одной групповой вставкой, причём каждая строка содержит не только признак аномальности, но и сенсор с наибольшим отклонением, величину его z-оценки и оценки обоих детекторов; каждый прогон предварительно фиксируется в журнале прогонов с его метаданными. Пакетная вставка вместо построчной снижает число обращений к базе при большом объёме обрабатываемых точек.

Результаты предиктивного контура хранятся в двух формах, различающихся способом записи. Снимок состояния прогноза - витрина для карточек мониторинга - содержит ровно одну строку на пару станок-сенсор и перезаписывается на каждом цикле прогноза. Перезапись реализована операцией вставки с обновлением при конфликте ключа: если строка для данной пары уже существует, её поля обновляются текущими значениями, иначе строка добавляется. Тем самым витрина всегда отражает актуальную картину, не накапливая историю. Чтобы карточка станка, который остановился или сменил фазу обработки и больше не присылает данные по этому сенсору, не застревала с устаревшим статусом, реализована чистка по времени: строки снимка, не обновлявшиеся дольше установленного срока, удаляются в конце каждого цикла.

Вторая форма - журнал предупреждений - ведётся в режиме только добавления: новая запись вносится лишь в момент возникновения предупреждения, на переходе от нормы к тревоге. В отличие от снимка, журнал не перезаписывается и не чистится по времени, поскольку он служит историей срабатываний предиктивного контура и используется при количественной оценке упреждения в главе 4. Такое разделение - перезаписываемый снимок для актуальной витрины и накапливаемый журнал для истории - обеспечивает одновременно наглядное текущее состояние и сохранность данных для последующего анализа.

Помимо двух описанных форм, в схеме предусмотрена таблица детального прогнозного ряда, хранящая прогноз поточечно: для каждой минуты истории и горизонта в ней записываются прогнозное значение, нижняя и верхняя границы доверительного интервала и фактическое значение. Эта таблица применялась на этапе настройки предиктивного контура: сохранение полных прогнозных рядов позволяло анализировать качество прогноза и подбирать параметры модели - длину обучающего окна, минимальное число точек и горизонт прогноза, - при которых модель давала наилучшие результаты. Запись в неё организована с перезаписью: перед сохранением нового прогноза предыдущий прогноз того же ряда удаляется, поэтому таблица не накапливает данные, а хранит лишь последний прогноз каждого сенсора. В итоговой конфигурации системы эта таблица не используется, так как рабочие витрины - снимок состояния и журнал предупреждений - самодостаточны.
