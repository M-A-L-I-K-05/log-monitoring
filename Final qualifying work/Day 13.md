# Day 13 — Калибровка детектора, починка обучения и разбор сценариев (конспект для пояснительной записки)

> Дата: 01.06.2026. В Day 12 выстроено гибридное правило детекции (z-max ⋁ ECOD/IForest + персистентность). Этот день: (1) найдена и устранена причина «потопа» ложных аномалий после доработок симулятора; (2) восстановлен задуманный режим обучения (сырые данные) с шумоподавлением на скоринге; (3) разобрана и зафиксирована точная механика сценариев (gradual/step) и их калибровка по σ. Раздел полезен для глав «модель и её обоснование» и «методика подготовки данных».

---

## 0. Контекст и симптом

После добавления в симулятор перемотки времени (+1/+10/+30 мин), паузы и пересборки данных (Restart с очисткой Loki) детектор стал выдавать **массу ложных аномалий** на нормальных данных (≈21 % точек, z до 28), хотя в Day 11–12 на непрерывном прогоне он работал чисто. Переобучение «на новых данных» не помогало. Задача дня — найти корневую причину, а не подкручивать пороги.

Опорный факт (из Day 11–12): граница брака = **3σ** (SPC), сценарий доводит сенсор до `mean ± 3σ`; зона до этого — ранний дрейф, который и должна ловить аналитика. Порог детектора `ANOMALY_Z = 2.8` (чуть раньше 3σ) → раннее предупреждение.

## 1. Правило z (ядро детекции) — напоминание

Модель хранит по каждому сенсору два числа из обучающего окна: `train_mean`, `train_std`. На скоринге:
```
z_i = (x_i − train_mean_i) / train_std_i      (та же σ, что в симуляторе)
is_anomaly = ( max_i |z_i| ≥ ANOMALY_Z )  ⋁  ECOD  ⋁  IForest
```
Берётся **максимум** по сенсорам (не сумма) → один выскочивший сенсор не «разбавляется» нормальными. Затем фильтр **персистентности по-канально**: аномалия пишется, только если хотя бы один «горячий» канал держится `PERSIST_N = 3` точек подряд (шум, прыгающий между сенсорами, серию не копит; устойчивый дрейф — копит).

**Главный вывод дня про z:** правило целиком зависит от `train_std`. Если `train_std` не соответствует реальному разбросу скоринговых данных — z systematically врёт. Всё расследование — про это несоответствие.

## 2. Корневая причина «потопа»: занижение σ через `resample().ffill()`

### 2.1 Цепочка диагностики
1. Почти все ложные срабатывания шли от **z-правила** (top_sensor_z ≥ 2.8), не от ECOD/IForest. z доходил до 28 — это не шум (шум даёт z≈1), а структурное несоответствие.
2. Сравнение нормы модели с живыми данными (shaving): `train_std` сенсоров оказалась в **3–6 раз уже** реального разброса. Модель меряла «громкие» данные «тихой» линейкой.
3. Прямая проверка показала: обучающие данные одной комбинации (turning/HEL-M) были размазаны на **≈4 виртуальных дня**, при этом **82 % минутных интервалов — пустые**.

### 2.2 Механизм
Станок шлёт сенсорику **только в фазе running**; в простоях/паузах/после перемотки — дыры. Подготовка фичей для обучения делала `resample('1min').mean().ffill()`. На рваных данных `ffill` забивает пустые минуты **плоским повтором** последнего значения → дисперсия схлопывается:

| сенсор (turning) | реальная σ (без ffill) | σ после ffill |
|---|---|---|
| coolant_temp_c | 0.66 | **0.32** |
| spindle_load_percent | 2.38 | **1.42** |
| vibration_rms_mm_s | 0.080 | **0.062** |

Заниженная вдвое+ `train_std` → на скоринге (где данные плотные, разброс настоящий) z раздувается → потоп.

### 2.3 Почему «раньше работало, теперь — нет»
- **Раньше:** непрерывный прогон → плотные данные без дыр → `ffill` ничего не портил → `train_std` = реальной.
- **Теперь:** перемотка/паузы/Restart → рваные данные на много дней → `ffill` схлопывает σ.
Триггер — не обрезка гаусса и не логика детекции, а **взаимодействие рваных данных и `ffill` в подготовке обучающей выборки**.

> Важно для записки: обрезка гаусса (clip 2.5σ) σ почти не меняет (срез ~5 %); она НЕ масштабирует разброс. Это частая ошибочная гипотеза.

## 3. Фикс: асимметрия обучение/скоринг (сырое обучение + минутное шумоподавление)

### 3.1 Что сделали (`ml/features.py::type_product_frames`)
Обучение теперь идёт на **сырых последних `TRAIN_POINTS` показаниях — БЕЗ resample и БЕЗ ffill**. Дополнительно — пивот **помашинный с конкатенацией строк** (а не общий `pivot_table(aggfunc='mean')` по `event_time`, который усреднял разные станки одного типа, попавшие в один момент, и тоже занижал σ). Скоринг (`machine_frames`) — без изменений: там `resample('1min')` остаётся.

### 3.2 Зачем именно так (задуманный режим)
Получается намеренная **асимметрия линейки и данных**:
- **Обучение → сырая 15-секундная σ** («громкая»). Для vibration ≈ 0.21.
- **Скоринг → минутные средние** (усреднение 4 показаний → шум /√4 = σ/2 ≈ «тихая» 0.1).

Тогда:
- **шум на скоринге** даёт `z ≈ (σ/2)/σ = 0.5` → до 2.8 не доходит, ложных нет;
- **дрейф сценария** (сдвиг среднего) усреднение сохраняет → `z_дрейф = Δ/σ₁₅` как был → ловится.

`train_mean` инвариантна к усреднению, поэтому центр не съезжает.

### 3.3 Проверка
На 264 610 нормальных точек по всем типам станков: **0** срабатываний z-правила, `z_max = 2.65` (< 2.8). До фикса — ≈21 % и z до 28. Сценарии при этом по-прежнему пробивают порог (сдвиг центра больше шума). Активная модель после фикса: `v2026-06-01_13-49-57`.

## 4. Запрос к Loki (методика подготовки данных) — зафиксировано

- **Обучение** (`fetch_for_training`): последние `TRAIN_FETCH_LIMIT` (150 000) **сырых** записей, `direction=backward`, **без узкого окна по времени** (только потолок Loki 29 дней). «Последние N» по факту прихода, не по времени — работает при любой скорости симулятора. Далее по каждой комбинации берутся последние `TRAIN_POINTS` (1000) сырых показаний.
- **Скоринг** (`fetch_events`): маленькое окно реального времени = интервал фона + запас (`SCORING_MARGIN_SEC`), «догоняющее» (растягивается до прошлого фетча, чтобы пачка логов после перемотки не потерялась). Дедуп по виртуальному `event_time`.
- Ось ряда — **виртуальное** `event_time` из JSON, не реальное время приёма Loki.

Жёсткие лимиты Loki (для записки): `max_entries_limit_per_query = 5000` (пагинация страницами), `max_query_length ≈ 30 дней`. Отдельный режим отказа — 500 «осиротевший чанк» при гонке очистки Loki на ходу (лечится остановкой Loki перед очисткой).

## 5. Генерация сенсорных данных — что статично, что дрейфует

`equipment.py::_generate_sensor_readings` и `furnace.py::_generate_furnace_readings`:
```
value = bounded_gauss(mean, std) × множитель_шестерни × модификатор_сценария   (станки)
value = bounded_gauss(mean, std) × модификатор_сценария                          (печь, по фазам)
```
- `bounded_gauss` — гаусс, обрезанный отбраковкой при |z|>2.5σ (нормальные данные физически не доходят до порога брака 2.8/3σ).
- Множитель шестерни — **константа** на тип шестерни.
- **Дрейфа в норме нет нигде.** Все сенсоры стационарны (фиксированные mean/std). Дрейф появляется **только от сценария** через `anomaly_modifier`. Печь: у каждой фазы свои фиксированные mean/std, между фазами скачок, внутри фазы — стационар (нагрев НЕ реализован как плавный подъём).

## 6. Сценарии: точная механика и калибровка

Каталог: `SCENARIOS_BY_MACHINE_TYPE[тип][сценарий]["sensors"] = {сенсор: базовый_множитель}`.
Severity: `SEVERITY_LEVELS = {light: sensor_scale 0.6, clear: 1.0, gross: 1.5}`.
Итоговый множитель сенсора: `target = 1 + (base_mult − 1) · sensor_scale`.

### 6.1 GRADUAL (под/пере-науглероживание печи; износ инструмента станков)
- Модификатор растёт **линейно** с дрейфом: `modifier(d) = 1 + (target − 1)·drift_progress`, `d ∈ [0,1]`.
- `drift_progress` растёт: станки +`pace` на деталь (`pace = 0.85/N`, N = 180/120/60 деталей для light/clear/gross); печь — шагами каждые 5 мин фазы carburizing, накапливается между загрузками.
- **Калибровка target — под 3σ при d = 0.85** (а НЕ от severity; severity для gradual = только темп):
  ```
  target = 1 ± 3·std / (0.85 · mean)
  ```
  Проверка: carbon_potential (mean 1.10, std 0.05) → `1 − 3·0.05/(0.85·1.10) = 0.840` ✓; vibration износа (mean 0.8, std 0.15) → `1.66` ✓.
- Отклонение центра в σ как функция дрейфа: `3·d/0.85`. Отсюда «лестница»:

  | drift d | отклонение | событие |
  |---|---|---|
  | **0.79** | 2.8σ | срабатывает детектор (раннее предупреждение) |
  | **0.85** | 3.0σ | `DRIFT_SCRAP_THRESHOLD` — деталь в брак |
  | **1.0** | 3.53σ | `DRIFT_STOP_THRESHOLD` — стоп, в обслуживание |

- Почему **0.85**: привязка к 3σ (предел SPC) при браковке; запас 0.15 до полного стопа = «станок ещё льёт брак»; детектор (2.8σ) ловит на 0.79 — до брака.

### 6.2 STEP (chatter, workpiece_loose, quench_distortion, coolant_loss…)
- Модификатор **константа** с первого тика (`drift_progress = 1.0`), без рампы; для печи — phase-lock в trigger-фазе.
- **Калибровка под 3σ при light** (severity для step = амплитуда):
  ```
  base_mult = 1 + 3·std / (0.6 · mean) = 1 + 5·std/mean
  ```
  Проверка: grinding vibration (mean 0.6, std 0.15) → `2.25` ✓ (= ровно 3σ при light); wheel_bearing (mean 47, std 3) → `1.32` ✓.
- Амплитуда по severity: **light 3σ, clear 5σ, gross 7.5σ** (масштаб 0.6/1.0/1.5).
- Оговорки: правило «3σ при light» — для **увеличиваемых** сенсоров. **Падающие** сенсоры (quench_oil_flow ×0.40, coolant_flow ×0.30) на это правило не сажали — они валятся резче (×0.40 при light ≈ −10.8σ, т.к. std маленький относительно падения; намеренно — однозначный признак).

### 6.3 Мультипликативность (важный нюанс для записки)
`value = gauss(mean,std) × m` ⇒ `value ~ N(mean·m, std·m)`: масштабируются И центр, И шум. Значит при UP-сценарии (m>1) шум растёт ∝ m, при DOWN (m<1) — сжимается. Для детекции главное — сдвиг центра (`3σ·d/0.85`); шум вокруг центра лишь рассыпает точки. Альтернатива — **аддитивный** дрейф (`value = gauss + offset`), который двигает только центр, оставляя шум постоянным (физически часто реалистичнее). Сейчас — мультипликативный.

## 7. Prophet: причина «молчания» и фикс норма-полосы

**Симптом:** предиктивный контур то пуст (даже при активном сценарии), то редкие ложные карточки без сценария. Должен ловить gradual-дрейф **раньше** детектора (по экстраполяции тренда).

**Причина — несоответствие масштаба полосы и ряда.** `_prophet_check_sensor` строит ряд по **минутным** средним (resample, σ≈σ_raw/2), а аномалию определяет как выход прогноза `yhat` за полосу `train_mean ± ANOMALY_Z·train_std`. После фикса обучения (раздел 3) `train_std` — **сырая 15с** (широкая). Значит полоса вдвое шире шкалы прогноза → `yhat` почти никогда её не пробивает. Замер на норме: полоса ±0.137, минутный ряд ±0.07, прогноз плоский (yhat 1.103→1.106) → запас 0.132, тишина. До фикса обучения `train_std` была ffill-заниженной (минутная, но ещё уже) → полоса слишком тесная → случайные ложные пробои. Один баг (масштаб) — оба симптома.

**Подтверждение:** синтетический дрейф (факт ещё в норме брака) — сырая полоса даёт 1 пробой (неустойчиво, тонет в шуме), минутная — 30 (весь горизонт), причём при факте на d≈0.44, т.е. **раньше детектора** (d≈0.79).

**Фикс:** норма-полоса Prophet считается по **минутной** σ.
- `detectors.MachineDetector` при обучении сохраняет `train_std_resampled = train_std / √n`, `n = бин_ресемпла/интервал_сенсора` (для 1min/15с = √4 = 2; шум симулятора i.i.d., поэтому √n точен).
- `pipeline._prophet_band_std` берёт `train_std_resampled` (фолбэк для старых моделей — пересчёт из сырой σ).
- Детекция и её сырая `train_std` — **нетронуты** (`config.SENSOR_INTERVAL_SEC` мирорит интервал симулятора).

**Принцип для записки:** норму надо мерить в **той же шкале, что и величина, с которой сравниваешь**. Детектор сравнивает минутное значение с сырой σ намеренно (демпинг шума, раздел 3); Prophet сравнивает прогноз минутного ряда — и для него полоса должна быть минутной. Один и тот же `train_std` для двух разных шкал — ошибка.

**Проверено:** норма → 0 ложных; синтетический дрейф → уверенный пробой с упреждением относительно детектора.
