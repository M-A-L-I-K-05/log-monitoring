# ML-сервис: полный разбор обучения и скоринга

Этот файл отвечает на вопросы: какие пакеты используются и зачем, где живут ECOD / Isolation Forest / Prophet, каким именно методом и какие данные «скармливаются» на обучении и на скоринге, и как/где хранятся обученные веса. Всё ниже сверено по коду (`ml/*.py`), ничего не выдумано.

Главная мысль, которую надо понять с самого начала:

> В сервисе **три разных механизма** обнаружения, и они «обучаются» и хранятся **по-разному**. Их легко перепутать, потому что они работают вместе. Поэтому сначала разделим их, а потом пройдём поток данных.

## 1. Пакеты: что это и зачем нужно

Из `ml/requirements.txt`:

| Пакет | Это что | Зачем в проекте |
|-------|---------|-----------------|
| **pandas** | библиотека таблиц (как Excel в коде): `DataFrame` — таблица, `Series` — один столбец | превращает сырые строки логов в таблицы, группирует по станку/детали, усредняет по минутам (`resample`), разворачивает «длинную» таблицу в «широкую» (`pivot_table`) |
| **numpy** | массивы чисел и быстрая математика над ними | ECOD и IForest едят не таблицу pandas, а «голый» массив чисел `numpy`. Переход делается через `.values` |
| **scipy** | научная математика (статистика, оптимизация) | напрямую почти не зовём; нужен как фундамент, на нём стоят scikit-learn и PyOD |
| **scikit-learn** | главная классическая ML-библиотека Python | сам по себе мы его не импортируем, но **Isolation Forest исторически родом отсюда**, и PyOD внутри использует именно sklearn-овский `IsolationForest` |
| **pyod** | Python Outlier Detection — библиотека **детекторов выбросов** | отсюда мы напрямую берём **ECOD** и **IForest** (см. ниже) |
| **prophet** | модель **прогноза временных рядов** (разработана в Meta/Facebook) | предиктивный контур: строит прогноз тренда сенсора на 30 минут вперёд. Внутри считает на Stan через `cmdstanpy` |
| **joblib** | сохранение Python-объектов на диск (сериализация) | замораживает обученный детектор в файл `.joblib`, чтобы не переобучать каждый раз |
| **fastapi** + **uvicorn** | веб-фреймворк и сервер | даёт эндпоинты `/train`, `/run-once`, `/evaluate` и т.д. |
| **requests** | HTTP-клиент | ходит в Loki за логами |
| **psycopg** + **psycopg-pool** | драйвер PostgreSQL | пишет результаты анализа в базу |
| **python-json-logger** | логи в формате JSON | сам сервис пишет структурированные логи |

### Где конкретно живут три алгоритма

```python
# ml/detectors.py
from pyod.models.ecod import ECOD        # ECOD — отсюда
from pyod.models.iforest import IForest  # Isolation Forest — отсюда (обёртка над sklearn)

# ml/forecaster.py
from prophet import Prophet              # Prophet — отсюда
```

- **ECOD** (Empirical-Cumulative-distribution-based Outlier Detection) — из `pyod`.
- **IForest** (Isolation Forest) — из `pyod`, но под капотом это `sklearn.ensemble.IsolationForest`.
- **Prophet** — из пакета `prophet`, отдельная история (см. раздел 6).

## 2. Три механизма обнаружения — не путать

| Механизм | Что это по сути | «Веса» = что именно | Когда обучается |
|----------|------------------|---------------------|------------------|
| **z-правило** | школьная статистика: на сколько сигм сенсор отклонился от своего среднего | два числа на каждый сенсор: **среднее** `train_mean` и **разброс** `train_std` | один раз, при `/train` |
| **ECOD** | непараметрический детектор: смотрит, насколько точка «в хвосте» распределения по каждой оси | внутреннее состояние объекта `ECOD` (распределение обучающих точек) | один раз, при `/train` |
| **IForest** | строит случайные деревья; выброс «изолируется» за меньшее число разрезов | набор случайных деревьев внутри объекта `IForest` | один раз, при `/train` |
| **Prophet** | прогноз тренда ряда вперёд | **весов не хранит вообще** — обучается заново на каждом цикле | каждый прогнозный цикл, на лету |

Ключевой момент, который снимает путаницу из вопроса:

- **z-правило НЕ обучается «через» ECOD или IForest.** Это три **независимые** вещи. z-правило — это просто `mean` и `std`, посчитанные обычными `X.mean()` и `X.std()`. ECOD и IForest — отдельные объекты со своими `.fit()`.
- Итоговое решение «аномалия или нет» — это **ИЛИ** трёх сигналов: сработало z-правило **или** ECOD **или** IForest (см. `detectors.py:147`). z-правило — главный триггер, ECOD/IForest — вспомогательные, докидывают «странные комбинации сенсоров».

## 3. Обучение (`/train`): поток данных по шагам

Запускается `pipeline.Pipeline.train()` (`ml/pipeline.py:75`). Идём по цепочке функций.

### Шаг 1. Достать логи из Loki

```python
records = loki_client.fetch_for_training()   # pipeline.py:83
```

`fetch_for_training()` (`loki_client.py:134`) просит у Loki последние `TRAIN_FETCH_LIMIT = 150000` строк события `sensor_reading` от сервиса `equipment`. На выходе — **список Python-словарей** (каждый словарь = одна распарсенная JSON-строка лога). Это ещё **не** pandas, просто список `dict`.

### Шаг 2. Список словарей → «длинная» таблица pandas

```python
long_df = features.records_to_long(records)   # pipeline.py:84
```

`records_to_long()` (`features.py:14`) разбирает каждый лог: из него достаёт `event_time` (виртуальное время завода), `machine_id`, `machine_type`, `product_code` и словарь показаний `readings = {sensor: value, ...}`. Каждое показание становится **отдельной строкой** таблицы:

```
event_time           machine_id  machine_type  product_code  sensor               value
2026-06-05 10:00:00  M-LATHE-01  turning       STD-A         vibration_rms_mm_s   0.81
2026-06-05 10:00:00  M-LATHE-01  turning       STD-A         spindle_load_percent 47.2
...
```

Это и есть «pandas преобразует строки логов в таблицу». Формат называется **длинный** (long): одна строка = одно число одного сенсора.

### Шаг 3. Группировка и «широкая» таблица под обучение

```python
tp_frames = features.type_product_frames(long_df)   # pipeline.py:85
```

`type_product_frames()` (`features.py:171`) — самая важная функция подготовки. Она:

1. группирует данные по **(тип станка, тип детали)** — например `(turning, STD-A)`. Модель учится **не на конкретный станок**, а на пару «тип станка + тип шестерни», потому что физика одинакова для всех станков этого типа на этой детали;
2. для каждой такой группы делает `pivot_table` — разворачивает длинную таблицу в **широкую** (wide): строка = момент времени, столбцы = сенсоры:

```
event_time           vibration_rms_mm_s  spindle_load_percent  spindle_bearing_temp
2026-06-05 10:00:00  0.81                47.2                  44.9
2026-06-05 10:00:15  0.79                46.8                  45.1
```

3. берёт **последние `TRAIN_POINTS = 1000`** показаний;
4. **важно: без `resample` и без `ffill`** — то есть на сырых 15-секундных показаниях. Это сделано намеренно (`features.py:178-185`): если заполнять дыры простоя станка плоскими повторами, разброс `std` искусственно занизится, и потом на скоринге z раздуется → потоп ложных тревог.

На выходе словарь: `{(тип_станка, деталь): (число_точек, широкая_таблица)}`.

### Шаг 4. Обучить детектор на каждой комбинации

В цикле по комбинациям (`pipeline.py:90`):

```python
det = MachineDetector(key, contamination=contamination)
det.fit(wide, machine_type=mtype)   # вот здесь происходит само обучение
```

Внутри `MachineDetector.fit()` (`detectors.py:50`) — **вот те самые «методы скармливания»**:

```python
X = wide.dropna()              # убрали пустые строки
# (а) ECOD
self.ecod = ECOD(contamination=self.contamination)
self.ecod.fit(X.values)        # ← скармливаем numpy-массив чисел

# (б) Isolation Forest
self.iforest = IForest(contamination=..., random_state=42)
self.iforest.fit(X.values)     # ← тот же массив

# поднимаем порог детекторов до mean + 3*std их «скоров» на обучении
s = self.ecod.decision_scores_
self.ecod.threshold_ = s.mean() + 3.0 * s.std()
# (то же для iforest)

# (в) z-правило — это просто два числа на каждый сенсор
self.train_mean = X.mean()                 # среднее по каждому столбцу-сенсору
self.train_std  = X.std(ddof=0).replace(0, np.nan)   # разброс по каждому сенсору

# отдельная «тихая» сигма для Prophet-полосы (см. раздел 6)
_n = бин_ресемпла / интервал_сенсора            # 60с / 15с = 4
self.train_std_resampled = self.train_std / np.sqrt(_n)   # σ/2
```

Разберём по пунктам вопроса:

- **`X.values`** — это и есть «превращение таблицы pandas в список чисел». `.values` отдаёт двумерный numpy-массив (строки × сенсоры). Именно его едят `ecod.fit(...)` и `iforest.fit(...)`.
- **«Скармливают тремя методами»** — да, но это три **разные** вещи:
  - `self.ecod.fit(X.values)` — обучение ECOD;
  - `self.iforest.fit(X.values)` — обучение Isolation Forest;
  - `X.mean()` и `X.std()` — это **не** обучение ECOD/IForest, это отдельный расчёт «нормы» для z-правила. Никакой `.fit()` тут нет, просто посчитали среднее и стандартное отклонение.
- **Что становится «весами»** после `fit`: обученный `self.ecod`, обученный `self.iforest`, и два ряда чисел `self.train_mean` / `self.train_std` (+ производная `train_std_resampled`). Всё это — поля объекта `MachineDetector`.

### Шаг 5. Заморозить веса на диск

```python
manifest = model_store.save_version(new_detectors, ...)   # pipeline.py:107
```

`save_version()` (`model_store.py:60`) для каждого обученного детектора делает:

```python
joblib.dump(det, ".../turning__STD-A.joblib")
```

`joblib.dump` сохраняет **весь объект `MachineDetector` целиком** — вместе с `ecod`, `iforest`, `train_mean`, `train_std`, `train_std_resampled`, списком колонок и метаданными. Подробнее о хранении — раздел 7.

## 4. Скоринг (`/run-once`, фоновый цикл): как применяются веса

Запускается `Pipeline.run_once()` (`pipeline.py:138`). Похоже на обучение, но данных мало (только свежее окно) и вместо `.fit` зовутся `.decision_function` / `.predict`.

### Шаг 1-2. Достать свежее окно и собрать таблицу

```python
records = loki_client.fetch_events(...)        # маленькое окно, последние секунды
long_df = features.records_to_long(records)
frames  = features.machine_frames(long_df)     # pipeline.py:153
```

Отличие от обучения: `machine_frames()` (`features.py:127`) **усредняет по минутам** (`resample("1min").mean()`) и заполняет короткие дыры (`ffill`). Почему усредняем именно на скоринге, а на обучении нет — см. длинный комментарий `config.py:38`: усреднение 4 показаний по 15с делает шум в √4 = 2 раза тише, поэтому случайные хвосты шума не дотягивают до порога, а реальный дрейф (сдвиг среднего) усреднение сохраняет.

### Шаг 3. Применить детектор

Для каждого станка берём **его** обученный детектор по ключу `тип__деталь` и зовём `det.score(wide)` (`detectors.py:104`):

```python
ecod_s = self.ecod.decision_function(X.values)   # «насколько аномально» (число)
ecod_l = self.ecod.predict(X.values)             # метка 0/1
if_s   = self.iforest.decision_function(X.values)
if_l   = self.iforest.predict(X.values)

# z-правило: на сколько сигм каждый сенсор отклонился от обученной нормы
z = (X - self.train_mean) / self.train_std       # используем сохранённые веса!
z = z.abs()
top_sensor_z = z.max(axis=1)                     # берём МАКСИМУМ по сенсорам

# Итог — ИЛИ трёх источников:
z_flag   = top_sensor_z >= ANOMALY_Z             # ANOMALY_Z = 2.8
det_flag = (ecod_l == 1) | (if_l == 1)
is_anomaly = z_flag | det_flag
```

Здесь хорошо видно, что **на скоринге z-правило берёт `train_mean` и `train_std`, сохранённые на обучении**. Берётся `max` по сенсорам (а не сумма) специально: один выскочивший сенсор виден всегда, сколько бы нормальных ни было рядом.

### Шаг 4. Персистентность (фильтр от случайного шума)

`_apply_persistence()` (`pipeline.py:232`): точку записываем как аномалию, только если «горячий» канал держится **`PERSIST_N = 3`** отсчёта **подряд**. Это правило SPC (run-rule). Случайный одиночный хвост гаусса так отсекается, а устойчивый дрейф — проходит. Счётчик ведётся по каждому каналу отдельно, поэтому шум, прыгающий с сенсора на сенсор, серию не копит.

### Шаг 5. Записать в Postgres

`store.insert_anomalies()` (`store.py:187`) пишет результат в таблицу `ml_anomalies` — это уже не веса, а результаты для Grafana.

## 6. Prophet — почему он стоит особняком

Prophet устроен **иначе**, и в вопросе это самое тонкое место.

### Prophet не хранит весов и обучается каждый раз заново

В отличие от детектора (обучили один раз → лежит на диске), Prophet **нигде не сохраняется**. Каждый прогнозный цикл он обучается с нуля на свежем ряду. Смотрим `forecaster.forecast_series()` (`forecaster.py:30`):

```python
dfp = pd.DataFrame({"ds": s.index, "y": s.values})   # Prophet требует РОВНО колонки ds и y
m = Prophet(weekly_seasonality=False, yearly_seasonality=False,
            daily_seasonality=False, interval_width=0.99)
m.fit(dfp)                                            # обучение на лету
future = m.make_future_dataframe(periods=30, freq="min")   # 30 минут вперёд
fc = m.predict(future)                                # yhat, yhat_lower, yhat_upper
```

- `ds` — это столбец времени, `y` — значения сенсора. Это **жёсткое требование** Prophet: он понимает только такие имена.
- `m.fit(dfp)` — Prophet сам внутри подбирает тренд. Сезонность выключена, потому что завод работает 24/7 и на синтетике Prophet иначе «выдумает» циклы.
- `m.predict(future)` даёт прогноз `yhat` и доверительный коридор `yhat_lower / yhat_upper` (ширина 0.99).

### А вот «норму» Prophet берёт НЕ у себя, а у детектора

Это прямой ответ на вопрос «какие переменные Пророк берёт для нормального среднего и смещения и кто туда что сохраняет».

Prophet сам по себе **не знает**, где «норма» сенсора. Он умеет только продлить тренд вперёд. Решение «прогноз вышел за норму» принимается в `_prophet_check_sensor()` (`pipeline.py:391`), и норма берётся **из обученного детектора**:

```python
mean = float(det.train_mean[sensor])        # среднее — сохранил MachineDetector.fit
std  = float(det.train_std[sensor])         # разброс — сохранил MachineDetector.fit
band_std = self._prophet_band_std(det, sensor, std)   # «тихая» σ (train_std_resampled)

lower = mean - ANOMALY_Z * band_std          # ANOMALY_Z = 2.8
upper = mean + ANOMALY_Z * band_std

future = fc[fc["actual"].isna()]             # только горизонт (будущее)
over = (future["yhat"] < lower) | (future["yhat"] > upper)
is_anom = over.sum() > 0                      # прогноз пробил норму → предиктивная аномалия
```

Итак, по переменным:

- **нормальное среднее** = `det.train_mean[sensor]` — кладёт туда значение `MachineDetector.fit` при обучении детектора (`detectors.py:69`);
- **нормальный разброс** = `det.train_std[sensor]`, а для полосы — `det.train_std_resampled[sensor]` (та же сигма, делённая на √4, потому что Prophet прогнозирует минутный ряд, который вдвое «тише» сырого 15-секундного) — тоже кладёт `MachineDetector.fit` (`detectors.py:70-76`);
- **граница нормы** = `mean ± 2.8 · band_std`;
- Prophet даёт только `yhat` (куда уйдёт тренд), а сравнение с границей делает уже pipeline.

То есть два механизма **связаны через детектор**: детектор при обучении сохраняет норму, а предиктивный контур эту норму переиспользует, добавляя сверху прогноз тренда. Веса Prophet при этом не существуют — он каждый раз эфемерный.

### Куда пишется результат Prophet

- `ml_prophet_status` (`store.py:240`) — снимок-витрина, одна строка на (станок, сенсор), перезаписывается каждый цикл → карточки Grafana;
- `ml_prophet_events` (`store.py:282`) — журнал, строка пишется только на **фронте** (когда предупреждение впервые загорелось) → нужен для `/evaluate`, чтобы знать упреждение.

## 7. Где и как хранятся веса

### Веса детектора — на диске, в volume

`model_store.py` версионирует веса в каталоге `MODELS_DIR = /app/models`, который смонтирован как docker-volume `ml-models` (переживает пересборку контейнера):

```
models/
  ACTIVE                          ← текстовый файл: имя активной версии
  v2026-06-05_10-30-00__baseline/
    manifest.json                 ← метаданные: когда, на чём, по каким станкам
    turning__STD-A.joblib         ← сериализованный MachineDetector
    hobbing__STD-A.joblib
    furnace__carburizing.joblib
    ...
```

- **Что внутри `.joblib`**: весь объект `MachineDetector` целиком — обученные `ecod` и `iforest`, ряды `train_mean` / `train_std` / `train_std_resampled`, список колонок-сенсоров, метаданные обучения. `joblib.load()` (`model_store.py:96`) поднимает объект обратно в память — готовый к скорингу, переобучать не надо.
- **Версии**: каждое `/train` создаёт новую версию-каталог. Файл `ACTIVE` указывает, какую версию использует скоринг. В WebUI можно переключиться на любую сохранённую версию или удалить.
- **Загрузка при старте**: `_load_active_on_start()` (`pipeline.py:59`) при запуске сервиса читает `ACTIVE` и грузит детекторы в память.

### Веса Prophet — нигде

Prophet живёт только в оперативной памяти на время одного прогнозного цикла. После цикла объект `Prophet` выбрасывается. Хранить нечего — он дёшев в переобучении и всегда должен видеть самый свежий тренд.

### Результаты анализа — в Postgres (это НЕ веса)

| Таблица | Что хранит | Кто пишет |
|---------|------------|-----------|
| `ml_anomalies` | точечные аномалии детектора | `store.insert_anomalies` |

## 8. Короткий ответ на исходные вопросы

1. **scikit-learn** — классический ML, напрямую не зовём, но Isolation Forest родом оттуда и используется внутри PyOD. **pandas** — таблицы и подготовка данных. **numpy** — массивы чисел, которые едят детекторы. **PyOD** — даёт ECOD и IForest. **prophet** — прогноз тренда. **joblib** — сохранение весов.
2. **ECOD и IForest** — из пакета `pyod`; **Prophet** — из пакета `prophet`.
3. На обучении pandas собирает из логов **широкую таблицу**, а `.values` превращает её в numpy-массив. Этот массив скармливается **двумя** `.fit`: `ecod.fit(X.values)` и `iforest.fit(X.values)`. **Третья вещь — это не `.fit`**, а обычный расчёт `X.mean()` и `X.std()` для z-правила.
4. На скоринге веса применяются методами `.decision_function` / `.predict` (для ECOD/IForest) и формулой `(X - train_mean)/train_std` (для z-правила).
5. **Prophet** норму у себя не держит: «нормальное среднее» он берёт из `det.train_mean[sensor]`, «нормальный разброс» — из `det.train_std_resampled[sensor]`; обе переменные заполняет `MachineDetector.fit` при обучении детектора. Сам Prophet обучается заново каждый цикл (`m.fit(dfp)`) и весов не сохраняет.
6. **Веса детектора** лежат на диске как `.joblib` в volume `ml-models` (версии + указатель `ACTIVE`). **Веса Prophet** не хранятся. **Результаты** анализа (не веса) — в таблицах Postgres.
