# ML-сервис — учебный план (как разобраться по шагам)

> Цель этого документа: пройти ML-сервис **по порядку**, от общей картины к конкретике,
> с точными числами из кода и реальными запросами. Не абстрактно. Все значения —
> из `ml/config.py` и `simulator/config.py` на момент написания. Если меняешь конфиг —
> числа пересчитай.

---

## 0. Сначала — ВРЕМЯ. Это корень всей путаницы.

В системе **два времени**, и их нельзя смешивать:

- **Виртуальное время** — время «внутри завода». Симулятор гонит его ускоренно
  (x100, x1000…). Это то, что записано в поле `event_time` внутри каждого лога.
- **Реальное время** — настоящие часы на твоём компьютере. По нему Loki индексирует
  логи (когда они физически пришли), и по нему просыпается фоновый поток ML.

**Правило перевода:** при скорости S одна реальная секунда = S виртуальных секунд.

### Три РАЗНЫХ интервала — не путай их между собой

| Что | Значение | Какое время | Что это значит простыми словами |
|---|---|---|---|
| `SENSOR_INTERVAL_SEC = 15` | 15 сек | **виртуальное** | станок шлёт показание раз в 15 виртуальных секунд (4 раза в виртуальную минуту) |
| `BACKGROUND_INTERVAL_SEC = 120` | 120 сек | **реальное** | фоновый поток ML просыпается раз в 2 **реальные** минуты и делает один прогон |
| `REAL_LOOKBACK_MIN = 30` | 30 мин | **реальное** | за один прогон ML тянет из Loki логи за последние 30 **реальных** минут |
| `RESAMPLE_RULE = "1min"` | 1 мин | **виртуальное** | показания усредняются в корзины по 1 виртуальной минуте |
| `FORECAST_HORIZON_MIN = 30` | 30 мин | **виртуальное** | Prophet прогнозирует на 30 виртуальных минут вперёд |
| `FORECAST_EVERY_RUNS = 5` | каждый 5-й | — | прогноз делается не каждый прогон, а раз в 5 прогонов |

### Твой вопрос «зачем 2 минуты, это же на 100x очень много»

Ты смешал два числа. Разложим:

- **2 минуты (реальные)** — это НЕ сколько данных смотрит модель. Это просто **как часто
  она просыпается пересчитать**. Каждые 2 реальные минуты → один прогон.
- **Сколько данных смотрит** — это `REAL_LOOKBACK_MIN = 30` реальных минут логов.

Конкретно на **x100**:
- 30 реальных минут логов = 30 × 100 = **3000 виртуальных минут ≈ 2 виртуальных дня** данных за один прогон.
- За эти 2 виртуальных дня каждый станок прислал 4 показания/мин × 3000 = 12000 показаний,
  которые ужимаются ресемплом в ~3000 строк (по 1 виртуальной минуте).

То есть «2 минуты» к объёму данных отношения не имеют — это таймер пробуждения.

## 1. Карта: кто с кем говорит (конкретно)

```
СИМУЛЯТОР ──HTTP POST──> сервисы (equipment и др.) ──пишут JSON-лог──> stdout
                                                                          │
                                                          Promtail собирает stdout
                                                                          ▼
                                                                        LOKI
                                                                          │
                          ML тянет логи (HTTP GET /loki/api/v1/query_range)
                                                                          ▼
                                                                      ML-СЕРВИС
                                                       (считает аномалии + прогноз)
                                                                          │
                                              пишет результаты (SQL INSERT)
                                                                          ▼
                                                                     PostgreSQL
                                                                          │
                                            Графана читает (SQL SELECT)
                                                                          ▼
                                                                      GRAFANA
```

**Важно:** ML-сервис **никогда** не обращается к Графане напрямую. Он только пишет в
Postgres. Графана сама ходит в Postgres и рисует. Это две независимые стороны.

## 2. Что ML забирает из Loki — ТОЧНО

Файл: `ml/loki_client.py`, функция `fetch_events`.

**Запрос (LogQL):**
```
{service_name="equipment", event="sensor_reading"}
```
за окно `[сейчас − 30 реальных минут ; сейчас]` по реальному времени.

То есть он просит у Loki: «дай все логи сервиса equipment с типом sensor_reading,
которые физически пришли за последние 30 реальных минут».

**Что в каждом логе (один sensor_reading):**
```json
{
  "service": "equipment",
  "event": "sensor_reading",
  "entity_id": "M-FRN-01",
  "event_time": "2026-01-09T14:30:00",      ← виртуальное время
  "details": {
    "machine_type": "furnace",
    "readings": {
      "carbon_potential": 0.84,
      "furnace_temp_zone1": 1.0152,
      ...
    }
  }
}
```

**Для разметки качества** (`/evaluate`) ML отдельно тянет:
```
{service_name="quality", event="scenario_event"}
```
— это сигналы start/stop/auto_completed сценариев, чтобы знать, где «правильный ответ».

## 3. Что ML делает с этими данными (конвейер одного прогона)

Файл: `ml/pipeline.py`, метод `run_once`.

1. **Тянет логи** из Loki (см. п.2).
2. **`features.py`** превращает плоский список логов в таблицу на каждый станок:
   строка = 1 виртуальная минута, столбцы = сенсоры (ресемпл по `event_time`).
3. **`detectors.py`** — по каждому станку обученный детектор (ECOD + IForest) ставит
   каждой минуте вердикт `is_anomaly` + оценки + виновный сенсор.
4. **`forecaster.py`** (только каждый 5-й прогон, только для главных сенсоров станка) —
   Prophet строит прогноз на 30 виртуальных минут вперёд и помечает `breach`
   (факт вышел за доверительный коридор).
5. **`store.py`** пишет результаты в Postgres: `ml_anomalies`, `ml_forecasts`, `ml_runs`.

**КРИТИЧНО:** если для станка **нет обученной модели** — он попадает в `untrained` и
**пропускается целиком**: ни аномалий, ни прогноза. Поэтому без обучения Графана пустая.

---

## 4. Что Prophet делает — конкретно

- **Вход:** один ряд одного сенсора за окно (напр. `carbon_potential` печи,
  ~по 1 точке на виртуальную минуту за последние 30 реальных минут данных).
- **Обучается** на этом ряду каждый раз заново (Prophet не замораживается — почему,
  см. отдельное обсуждение: на стационарных данных заморозка дала бы плоскую полосу,
  это дублировало бы ECOD; ценность Prophet — продлить ТЕКУЩИЙ тренд вперёд).
- **Отдаёт:** для каждой точки `yhat` (прогноз), `yhat_lower`/`yhat_upper` (коридор),
  `actual` (факт), `breach` (факт вне коридора). Плюс 30 виртуальных минут вперёд.
- **Главные сенсоры для прогноза** (`MAIN_SENSORS` в `ml/config.py`):
  - furnace → `carbon_potential`, `furnace_temp_zone1`
  - turning → `vibration_rms_mm_s`, `spindle_load_percent`, `spindle_bearing_temp`
  - и т.д. Детекция использует ВСЕ сенсоры, прогноз — только эти.

## 5. Что уходит в Графану — ТОЧНО

ML пишет в три таблицы Postgres, Графана читает их SQL-ом (datasource uid
`PCC52D03280B7034C`). Примеры реальных запросов панелей:

```sql
-- сколько аномалий в последнем прогоне
SELECT n_anomalies FROM ml_runs WHERE kind = 'run' ORDER BY run_id DESC LIMIT 1;

-- таблица последних аномалий
SELECT event_time, machine_id, top_sensor, top_sensor_z, score_ecod, score_iforest
FROM ml_anomalies WHERE is_anomaly ORDER BY id DESC LIMIT 200;

-- сколько прогнозов пробили коридор
SELECT count(*) FROM ml_forecasts WHERE breach;

-- выпадающий список станков в верхнем меню (вот почему он пустеет после reset!)
SELECT DISTINCT machine_id FROM ml_forecasts ORDER BY 1;
```

**Поэтому:** список станков в Графане = `SELECT DISTINCT machine_id FROM ml_forecasts`.
Нет прогнозов → пустой список. Прогнозы пишутся только при «Детекция + прогноз»
(не при обычной «Детекция») и только если модель обучена.

**Ещё одна ловушка времени:** в таблицах лежит **виртуальное** время (`event_time`).
Поэтому на дашборде диапазон времени зафиксирован (2026-01-01…2027), иначе Графана
(которая по умолчанию показывает «последний час реального времени») ничего не найдёт.

## 6. Справочник endpoint'ов (что нажимаешь → что зовётся)

| Endpoint | Кнопка в WebUI | Что делает |
|---|---|---|
| `GET /health` | бейдж Loki | живой ли сервис, доступен ли Loki |
| `GET /status` | (авто) | активная версия весов, обученные станки, режим |
| `POST /train` | Обучить | обучить детекторы → сохранить версию на диск |
| `GET /models` | таблица версий | список сохранённых версий весов |
| `POST /models/activate` | Подключить | загрузить версию в работу |
| `DELETE /models/{v}` | Удалить | удалить версию с диска |
| `POST /detect` | Детекция | скоринг (только аномалии) |
| `POST /forecast` | Детекция + прогноз | скоринг + Prophet |
| `POST /evaluate` | Оценка качества | метрики по разметке сценариев |
| `POST /loop` | Применить режим | вкл/выкл фон, интервал, авто-ретрейн |
| `POST /reset` | Сбросить результаты | очистить таблицы результатов (веса не трогает) |

## 7. Пошаговый план изучения (делай по порядку)

Каждый шаг: **прочитай → запусти → посмотри глазами**. Не беги вперёд.

**Шаг 1. Время.** Перечитай раздел 0. Открой `ml/config.py` и `simulator/config.py`,
найди все 6 чисел из таблицы. Убедись, что понимаешь, какое реальное, какое виртуальное.

**Шаг 2. Один лог.** Запусти симулятор, открой логи: `docker logs equipment | grep sensor_reading | head`.
Найди в JSON поля `event_time`, `entity_id`, `readings`. Это сырьё для ML.

**Шаг 3. Запрос к Loki.** Открой `ml/loki_client.py::fetch_events`. Повтори запрос руками:
```bash
curl -s -G 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode '{service_name="equipment", event="sensor_reading"}' \
  --data-urlencode "start=$(date -d '10 min ago' +%s)000000000" \
  --data-urlencode "end=$(date +%s)000000000" --data-urlencode 'limit=2'
```
Увидь, что приходит ровно то, что в Шаге 2.

**Шаг 4. Фичи.** Открой `ml/features.py`. Пойми: список логов → таблица (строка=минута,
столбцы=сенсоры). Это вход детектора.

**Шаг 5. Детектор.** Открой `ml/detectors.py`. Раздел `score()` — что на входе (таблица),
что на выходе (по строке вердикт + оценки + top_sensor). См. отдельный разбор с числами.

**Шаг 6. Прогноз.** Открой `ml/forecaster.py`. Раздел 4 этого документа.

**Шаг 7. Запись.** Открой `ml/store.py`. Три таблицы, три INSERT-а. Это всё, что видит Графана.

**Шаг 8. Прогон целиком вживую:**
1. Прогнать завод в норме (без сценариев) несколько реальных минут.
2. WebUI :8006 → «Обучить» (окно ~10 мин) → проверь `fitted`.
3. «Детекция + прогноз».
4. Открой Графану → станки появились, есть аномалии и прогнозы.
5. Запусти gradual-сценарий на печи → дождись отбраковки → снова «Детекция + прогноз»
   → посмотри, поймала ли модель.

**Шаг 9. Оценка.** Нажми «Оценка качества» (`/evaluate`). Разбери метрики:
`window_recall` (поймали ли окно сценария), `avg_lead_time_min` (за сколько до конца).

## 8. Частые «почему не работает»

- **Графана пустая / нет станков** → нет прогнозов в `ml_forecasts`. Причина почти всегда:
  (а) модель не обучена (нет активной версии), либо (б) делал «Детекция» вместо
  «Детекция + прогноз», либо (в) сделал «Сбросить результаты».
- **`/train` вернул `machines: 0`** → в окне нет данных. Симулятор стоит, либо окно
  задевает повреждённый чанк Loki (см. AI-заметку про дыры в Loki).
- **Prophet ничего не выдал** → прогноз идёт раз в 5 прогонов ИЛИ нет обученной модели
  ИЛИ диапазон времени дашборда не покрывает виртуальные `event_time`.
- **На графике «всё нормально», а отбраковка была** → аномалия по сенсору могла быть
  короткой и попасть в один ресемпл-бакет 1 мин; смотри таблицу `ml_anomalies`, а не
  только график прогноза.
