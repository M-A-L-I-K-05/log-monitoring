### 1. Рефакторинг 4 сервисов под обязательное event_time

#### Проблема, которая решалась

В сервисах было два бага:

- Использование `NOW()` в SQL-запросах — БД писала **реальное** время хоста, а не виртуальное симулятора. При запуске симулятора на ×100 в логах виртуальное время уехало бы вперёд, а в БД остался текущий момент. Полный рассинхрон.
- Дублирование таймстемпов: `asctime` из json-формирмера давал реальное время хоста, и плюс мы пытались добавить event_time. Получались два разных времени в одной записи.

#### Принятое решение

`event_time: datetime` — **обязательное** поле во всех Pydantic-моделях всех 4 сервисов. Без fallback, без `event_time or datetime.utcnow()`. Один путь в коде.

Сервисы используют `event_time` вместо `NOW()` в SQL:

```python
# было
"UPDATE machine_status SET state_changed_at = NOW() WHERE machine_id = %s"

# стало
"UPDATE machine_status SET state_changed_at = %s WHERE machine_id = %s",
(event_time, machine_id)
```

В логах event_time идёт как top-level поле через `extra`:

```python
logger.info(
    "sensor_reading",
    extra={
        "entity_id": data.machine_id,
        "event_time": data.event_time.isoformat(),
        "details": {...},
    },
)
```

#### Убрали лишние таймстемпы

Из json-формирмера удалили `asctime`/`timestamp`:

```python
formatter = jsonlogger.JsonFormatter(
    "%(levelname)s %(name)s %(message)s",  # без asctime
    rename_fields={
        "levelname": "level",
        "name": "service",
        "message": "event",
    },
)
```

Теперь в JSON-логе только одно время — `event_time` (виртуальное). Loki сам присваивает свой ingest-timestamp при приёме — он используется только для UI-сортировки, в аналитике опираемся на `event_time` из JSON.

#### Полностью отключили uvicorn-логи

Раньше пропагировались на root logger и забивали Loki спамом `INFO: 172.18.0.1:55432 - "POST /sensor-reading HTTP/1.1" 200 OK` на каждый запрос симулятора. На ×100 это десятки спама в секунду.

```python
for name in ("uvicorn", "uvicorn.error", "uvicorn.access"):
    uv_logger = logging.getLogger(name)
    uv_logger.handlers.clear()
    uv_logger.propagate = False
    uv_logger.disabled = True
```

Это симулятор, не реальный завод — access-логи для аудита не нужны. Производственные логи (sensor_reading, state_change, etc.) полностью покрывают что происходит.

### 2. Обсуждение и упрощение виртуальных часов

#### Исходный дизайн (избыточный)

Сначала придумали `VirtualClock` с auto-advance формулой:

```python
class VirtualClock:
    def __init__(self, start, speed=1.0):
        self._v_anchor = start
        self._r_anchor = time.monotonic()  # реальный якорь
        ...
    
    def now(self):
        elapsed = time.monotonic() - self._r_anchor
        return self._v_anchor + timedelta(seconds=elapsed * self._speed)
```

Идея: «часы — это формула, не процесс». Когда меняем скорость или ставим на паузу — делаем `rebase` (пересчитываем якорь, чтобы виртуальное время не прыгало).

#### Почему упростили

В тиковой модели (фоновый поток крутится с шагом 100мс) формула с monotonic избыточна. Достаточно просто инкрементировать переменную:

```python
# в SimulationState
self.virtual_time: datetime = SIM_START_TIME
self.speed: float = 1.0
self.running: bool = False

def advance_time(self, real_seconds):
    if self.running:
        self.virtual_time += timedelta(seconds=real_seconds * self.speed)
```

- Pause = `running = False`, время не двигается
- Resume = `running = True`, время продолжается
- Set_speed = меняем `self.speed`, на следующем тике инкремент будет другой
- Никаких якорей, никаких rebase, никаких monotonic — три поля в одном объекте

#### Что важно про monotonic в тиковой модели

Запутались в обсуждении: «а что будет с дельтой monotonic при рестарте контейнера»? Ответ — **в нашем дизайне monotonic вообще не нужен**. Время определяется счётчиком тиков, а не «реально прошедшим временем относительно якоря». Перезапуск = новый процесс = новый счётчик с виртуального START_TIME.

### 4. Принятые архитектурные решения после обсуждения

После обсуждения архитектуры приняли следующие решения. Многие изменили первоначальный дизайн.

#### Маршрут партии — единый для всех продуктов

Изначально планировалось две ветки маршрута (SPUR-S и HEL-L минуют shaving). Решили **упростить — все 4 продукта идут одним путём**:

```
turning → hobbing → shaving → heat_treatment → grinding → inspection
```

`product_code` остаётся важен **только для группировки в загрузках печи** (recipe-based scheduling). Разные продукты не смешиваются в одной загрузке.

#### Ордеры → партии по приоритету

- Ордеры стандартные: 100, 200 или 300 шт (равновероятно)
- Размер партии зависит от **приоритета**:
    - rush → партии по 25 (быстро переключаются)
    - urgent → партии по 50
    - normal → партии по 80 (эффективнее)
- Веса приоритетов: normal 75%, urgent 20%, rush 5%
- Веса продуктов: SPUR-S 35%, SPUR-M 30%, HEL-M 20%, HEL-L 15%

#### Интервал между ордерами — пересчитали!

Изначально написал 20-40 виртуальных минут — это **было неправильно**. Расчёт:

- Bottleneck — печь: 2 × 80 деталей / 490 мин ≈ 20 деталей/час = 480/день
- Средний ордер = 200 деталей → ~2.4 ордера/день максимум
- Интервал ≈ 24ч / 2.4 ≈ 10 виртуальных часов

**Финал: 4-8 виртуальных часов** (240-480 минут) случайно. Это создаёт лёгкое давление на очереди и иногда — полную утилизацию.

#### Партия целиком на станке + cooldown

- Партия захватывает станок целиком. Партия 80 идёт **полностью на один станок**, не делится на 3 лотка по 27.
- После завершения партии — станок в состоянии `cooldown` ещё **5 виртуальных минут** перед возвратом в `idle`. Это эмулирует физическое перемещение тележкой + подготовку к следующей партии.
- **Setup time увеличен с 2 до 7 минут** — эмулирует наладку оснастки, проверку программы.

#### Tool change — через maintenance, не отдельное состояние

Изначально планировалось отдельное состояние `tool_change` на станке (~5 мин). Решили **унифицировать**:

- Equipment-подсистема следит за `tool_wear` (0.0..1.0)
- При `tool_wear ≥ 0.95`: эмитим alarm `TOOL_WEAR_HIGH` + триггерим maintenance создать work_order с `priority="high"`, `reason="tool_wear_threshold"`
- Maintenance принимает наряд как обычное ТО (после того как станок выйдет из running)
- Бригада приходит, делает ТО, сбрасывает tool_wear = 0

Это убирает специальное состояние со станка. Конечный автомат короче: idle → setup → running → cooldown → idle (и иногда → maintenance → idle).

#### Quality в 3 точках вместо 1

Изначально quality срабатывал только на финальной inspection. Решили **добавить spot-check** на двух промежуточных стадиях:

1. **После hobbing** (spot-check): 1 случайная деталь, 2-3 измерения. Если fail → ещё 2 соседних (всегда pass в норме).
2. **После heat_treatment** (spot-check): то же самое.
3. **Финальная inspection**: 10% выборка с полным набором (3-5 измерений на деталь).

Это даёт **3 точки качественного сигнала** для ML вместо одной.

Также отказались от CMM, оставили **только GMM**: `M-GMM-01`, `M-GMM-02`.

#### Печь — recipe-based scheduling

Самая сложная подсистема. Логика:

- Очередь `waiting_furnace` перед обеими печами
- Когда печь свободна — алгоритм формирования загрузки:
    1. Смотрим голову очереди → её `product_code` = «рецепт»
    2. Из очереди отбираем партии того же рецепта, пока не превысим 80 деталей
    3. Старт загрузки если выполнено любое из:
        - заполнение ≥ 60% (48+ деталей)
        - голова ждёт ≥ 30 виртуальных минут
        - среди отобранных есть `rush`
- 6 фаз внутри загрузки: `loading (5min) → heating (120min) → carburizing (240min) → quenching (30min) → tempering (90min) → unloading (5min)` = **490 минут = 8 часов 10 минут**
- На каждой фазе свои сенсоры с реалистичными параметрами (профили в `config.FURNACE_SENSOR_PROFILES`)
- После unloading партии в очередь `queue_grinding`

#### 5 сценариев аномалий — заготовки

Заложили **архитектурный хук** для сценариев без полной реализации:

- В `Machine` добавлено поле `anomaly_modifier: dict[str, float]` — мультипликаторы для сенсорных значений
- При генерации `sensor_reading` значения умножаются на модификаторы (если заданы)
- `ScenariosController` имеет 5 методов-заготовок:
    1. `start_tool_wear_acceleration` — рост vibration_rms и spindle_load
    2. `start_bearing_overheat` — рост bearing_temp + vibration
    3. `start_furnace_drift` — дрейф температуры одной зоны печи
    4. `start_coolant_failure` — падение coolant_flow + рост coolant_temp
    5. `start_quality_burst` — повышенный fail rate на участке (TODO: подключить к QualitySubsystem)

#### Главный цикл (loop.py)

Простой фоновый поток. Каждый тик:

```python
def _run(self):
    while not self._stop_event.is_set():
        self.state.advance_time(TICK_REAL_SEC)
        if self.state.running:
            now = self.state.virtual_time
            for sub in self.subsystems:
                try:
                    sub.tick(now)
                except Exception as exc:
                    logger.exception("subsystem %s failed", sub.name)
        time.sleep(TICK_REAL_SEC)
```

Подсистемы вызываются **строго в порядке**: `orders → production → equipment → furnace → quality → maintenance → scenarios`

#### Состояние (state.py)

Один объект, держит всё. Защита RLock-ом. Виртуальное время — 3 поля прямо в нём. Снимок для `/status` берётся под lock-ом.

#### HTTP-клиент (client.py)

`requests.Session()` для keep-alive. Один метод = один HTTP-endpoint. Все методы добавляют `event_time` как ISO-строку в payload. При ошибках сети — лог и продолжаем, не падаем.

## Ключевые концепции для запоминания

### Что такое тик и главный цикл

**Тик** — одна итерация главного цикла. На каждом тике:

1. Виртуальное время продвигается на `TICK_REAL_SEC × speed`
2. Поочерёдно вызываются все подсистемы (`subsystem.tick(now)`)
3. `time.sleep(TICK_REAL_SEC)` — пауза 100 мс реального времени
4. Затем следующий тик

**Главный цикл** (main loop) — `while not stop_event.is_set():` в **отдельном фоновом потоке** (`threading.Thread(daemon=True)`). FastAPI-эндпоинты управления продолжают отвечать параллельно.

### Виртуальное время в тиковой модели

В отличие от auto-advance формулы — здесь просто три поля:

- `virtual_time: datetime` — текущий момент
- `speed: float` — множитель
- `running: bool` — флаг работы

Инкремент на каждом тике: `if running: virtual_time += timedelta(seconds=0.1 * speed)`.

Pause = `running = False`. Resume = `running = True`. Set_speed = поменять `speed`.

Никаких якорей, monotonic, rebase. Простой счётчик.

### Discrete Event Simulation (DES) vs time-stepped

**Чистый DES** (как в SimPy) — события генерируются вперёд, время прыгает к следующему запланированному событию. Эффективно по CPU, плохо стыкуется с HTTP/WebUI.

**Time-stepped** — фиксированный шаг во времени, на каждом шаге проверяем что нужно сделать.

**Мы взяли гибрид**: фиксированный тик 100 мс реального времени, виртуальное время продвигается умножителем. Подсистемы на каждом тике проверяют свои таймеры («прошло ли setup_time?», «пора ли sensor_reading?»).

### Stateless контейнеры и почему нет volume

В Docker-практике:

- Контейнер — это **процесс**, не место хранения
- У контейнера слоистая FS (overlay), один writable слой
- `docker rm` уничтожает этот слой → данные пропадают
- Состояние выносится в backing services (БД, volume)

Для нашего симулятора: рестарт = новый прогон. Никакой персистентности. Workflow: `docker compose down -v && docker compose up -d --build`. Флаг `-v` удаляет и именованные, и анонимные volume.

Для Postgres особенность: в образе объявлен `VOLUME /var/lib/postgresql/data`, поэтому даже без явного `volumes:` создаётся **анонимный** volume. Чтобы стопроцентно вычищать — нужен `down -v`.

### Партия целиком на станке

Принципиальное упрощение: партия 80 деталей идёт **полностью на один станок**, не делится. Параллелизм сохраняется на уровне разных участков (партия А на grinding, партия B на hobbing, партия C на turning одновременно).

Это **не потоковая обработка** (где детали идут одна за другой между разными станками). Здесь станок «занят» партией от первой до последней детали + cooldown.

Зачем: радикально упрощает state machine и трассировку. Соответствует серийному производству с перемещением кассетами.

### Recipe-based campaign scheduling печи

Индустриальная практика: партии с одинаковым «рецептом» (продуктом) группируются в одну «кампанию» в печи. Это позволяет:

- Не переключать set-points температуры между загрузками
- Не менять углеродный потенциал атмосферы
- Сохранять стабильные параметры цементации

В коде: алгоритм `_try_start_load` смотрит голову очереди, берёт её product_code как «рецепт», набирает партии того же продукта до 80 шт. Старт по условиям заполнения / ожидания / rush-приоритета.

### Anomaly modifier как хук для сценариев

Каждый Machine имеет поле:

```python
anomaly_modifier: dict[str, float] = field(default_factory=dict)
```

Когда equipment генерирует sensor_reading:

```python
value = random.gauss(mean, std)
modifier = machine.anomaly_modifier.get(sensor_name)
if modifier is not None:
    value *= modifier
```

Это **архитектурный хук**. Сценарии устанавливают модификаторы (например, `vibration_rms_mm_s: 1.5`), сенсоры начинают идти на 50% выше нормы. ML потом обнаруживает это как аномалию.

### FIFO через collections.deque

`collections.deque` — двусторонняя очередь с O(1) операциями `.append(x)` и `.popleft()`. Идеально подходит для FIFO в нашей модели:

```python
self.queues: dict[str, deque[Batch]] = {
    "pending": deque(),
    "queue_hobbing": deque(),
    ...
}

# добавить в хвост
self.state.queues["pending"].append(batch)

# взять из головы
batch = self.state.queues["pending"].popleft()
```

В отличие от `queue.Queue` — не thread-safe сама по себе, но у нас один поток-писатель (главный цикл), поэтому достаточно нашего общего lock-а.

### Lock для shared state

`threading.RLock()` (reentrant lock — можно взять повторно из того же потока). Защищает от гонок между:

- Фоновым потоком, который меняет состояние на каждом тике
- FastAPI-эндпоинтами (`/status`), которые читают состояние

Без lock-а `/status` мог бы вернуть «полусломанный» снимок: партии обновились, станки ещё нет.

В коде: все мутации состояния и `snapshot()` под `with self._lock:`. Подсистемы тоже берут lock на время своего `tick()`.

### Polling vs WebSocket для WebUI

Решение: **polling раз в секунду**. Причины:

- Простота: один endpoint `/status`, никакой stateful-логики на сервере
- Устойчивость: если симулятор перезапустится — UI просто продолжит запрашивать
- Достаточная скорость: 1 запрос/сек на 16 станков — пренебрежимая нагрузка

WebSocket был бы оправдан при >5 обновлений/сек — нам не нужно.

## Шероховатости и компромиссы

- **Синхронный HTTP**. На скорости ×1000 один тик = 100 виртуальных секунд = ~6 sensor_readings × 16 станков = ~100 запросов на тик. Реально пройдёт за 100мс благодаря keep-alive, но на грани. Если упрётся — добавим буфер `deque` и второй поток-flusher.
- **Linear tool wear**. В реальности износ нелинейный (экспоненциальный под конец срока). У нас линейный — упрощение.
- **24/7 завод**. Нет смен, обедов, выходных. Завод работает непрерывно.
- **Нет rework**. Деталь с fail просто помечается, не идёт на доработку.
- **Однопоточные подсистемы**. Все подсистемы крутятся в одном потоке последовательно. При большой нагрузке можно распараллелить, но усложнит lock-логику.
- **Симулятор не персистится**. Рестарт = новый прогон с виртуального `SIM_START_TIME`. Сознательно — для воспроизводимости экспериментов.
- **quality_burst сценарий не подключён** к QualitySubsystem. ScenariosController хранит метаданные, но QualitySubsystem пока их не читает. TODO для дня 6.
- **Сценарии — статичные модификаторы**. Нет градиентного ramp-up/down. Хочется чтобы tool_wear_acceleration постепенно поднимал vibration с 1.0× до 1.5× за 2 часа, а не сразу. Тоже на день 6.
